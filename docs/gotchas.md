# Things to avoid (Claude tends to get these wrong)

Topic-grouped list of footguns specific to this codebase. The top-level `CLAUDE.md` summarises this file with a one-line pointer; consult the relevant section when you're about to work on that area.

## AES (FIPS-197)

- **FIPS-197 has multiple appendices with DIFFERENT keys.** Appendix B uses key `2b7e1516…`, Appendix C.1 uses `000102…0e0f`, Appendix C.2 uses a 24-byte AES-192 key. *Don't quote a value from one appendix to test a vector from another.* Verify the key matches before asserting an intermediate state.
- **SubBytes and ShiftRows commute.** Both are byte-wise permutations; swapping their order in a round produces *identical* ciphertext. This is a real algebraic property, exploited by efficient AES implementations. If you're writing a "reordering changes the output" test, swap **ShiftRows ↔ MixColumns** instead.
- **The AES state matrix is column-major.** Byte at row `r`, col `c` lives at `bytes[r + 4*c]`. The first 4 bytes of the input go into column 0 (top-to-bottom), not row 0 (left-to-right). Visualization conventions sometimes invert this.
- **GF(2^8) uses the polynomial `x^8 + x^4 + x^3 + x + 1` (0x11b).** Don't use 0x1b alone (that's the reduction-when-MSB-is-set part of `xtime`).
- **Key expansion uses the FORWARD S-box, even when decrypting.** The inverse cipher consumes the same round keys in reverse order; it does not re-derive them with the inverse S-box. Both `aes-128.ts` and `aes-128-decrypt.ts` share the same `key-expansion` step verbatim.
- **AES-256 has an extra `i % Nk == 4` SubWord-only branch in key expansion.** When `Nk > 6`, every word at `i % Nk == 4` passes through SubWord WITHOUT RotWord and WITHOUT an Rcon XOR. Only AES-256 (Nk=8) triggers it — AES-128/192 never reach the branch. If you assert only the final round key, an end-to-end KAT can pass with a wrong intermediate by coincidence. `tests/aes-256-vectors.test.ts` asserts `roundKey.3` directly (= w[12..15], where w[12] is the first index that fires the branch) as the specific guard.
- **AES key length and `rounds` must agree: `rounds === Nk + 6`.** Key-expansion asserts this — a 24-byte key with `rounds: 10` (or any mismatched pair) throws "rounds (X) must equal Nk+6 (Y)". When writing a new AES-variant spec, both the `inputs.key.byteLength` and the key-expansion `rounds` param must move together.

## Padding overlay

- **PKCS#7 always adds at least one byte of padding.** When the raw input is already a clean block multiple, canonical PKCS#7 appends a FULL extra block of `blockSize`. The single-block UI caps input at `blockSize - 1` to avoid this case; the step itself implements the canonical behavior. Don't "optimize" by skipping padding when `input.length % blockSize === 0` — you'll break unpad.
- **`applyPaddingScheme` walks the TOP level of `spec.steps` only.** The four overlay step types (pkcs7-pad/unpad, load-block/store-block) are always inserted at the top level so a top-level filter cleanly strips them without descending into per-round groups. If a future scheme needs to insert leaves inside groups, the helper needs a deeper walk — don't sneak overlay leaves into nested groups.
- **The padding overlay is AES-only.** `load-block` is hardcoded for blockSize=16 (the 4×4 byte matrix). `applyPaddingScheme` early-returns for any spec whose `stateShape !== "matrix4x4-bytes"` AND has no iterate node (the single-block-AES detection), and the UI disables the padding `<select>` for non-AES ciphers. Multi-block AES specs reach the iterate branch instead — see next bullet. A future block-size-aware load/store rework can unlock the overlay for Speck and friends, but right now: don't try to apply padding to non-AES specs, and don't write tests that assume the overlay fires for them.
- **`applyPaddingScheme` has three branches now, not two.** Multi-block specs (detected by `kind: "iterate"` at the top level) get just `pkcs7-pad` prepended on encrypt or `pkcs7-unpad` appended on decrypt — NO `load-block` / `store-block` at the boundary, because the iterate body's `split-blocks` / `concat-blocks` steps handle the BytesState ↔ MatrixState transition internally. Single-block AES (`stateShape === "matrix4x4-bytes"`, no iterate) keeps today's `[pad, load-block]` / `[store-block, unpad]` shape. Non-AES (Speck) skips the overlay entirely. The branch order in `spec-mutations.ts::applyPaddingScheme` matters — iterate detection comes first.

## Multi-block / iterate

- **The iterate node delegates byte slicing to step executors.** The runtime never reads `state.bytes.subarray(i*16, (i+1)*16)` itself. Instead, a `split-blocks@1` step BEFORE the iterate writes `aux["plaintext-blocks"]: MatrixState[]`, and the iterate reads from that aux array each iteration. This keeps the executor signature `(state, params, ctx) → state` intact — no special "runtime can slice bytes" carve-out for iterate. When Phase 3 lands CTR, the same pattern: a step does the work, the iterate just walks the aux array. Don't put byte-slicing logic in the runtime.
- **Per-iteration step ids get a `:b{i}` suffix automatically.** A `round.1.sub-bytes` leaf inside an iterate emits `round.1.sub-bytes:b0`, `round.1.sub-bytes:b1`, … per iteration. The trace store's `setTrace` is stepId-anchored, so this is what makes "preserve focus across re-runs" work on a multi-block trace. Don't write step ids with literal `:b` substrings in them — they'd collide with the suffix convention. The runtime also stamps `frame.blockIndex` so renderers (`BlockBadge`) can show context without parsing the stepId.
- **`paddingLimits` got a fourth `cipherMode` arg with a default.** Existing call sites that don't pass it get `cipherMode = "single-block"` and behave identically to before — same ranges, same scheme-specific caps. The new arg is what widens the range for multi-block (0..255 PKCS#7-encrypt, 16..256 decrypt, etc.) up to `MAX_BLOCKS_UI × 16`. If you add a new call site in code that's mode-aware, plumb the cipherMode through; if you're calling from a single-block test, the default is the right answer.
- **Run handler's alignment check belongs in App.tsx, not deep in `split-blocks`.** Multi-block decrypt + multi-block encrypt-with-`none` both require input length % 16 == 0. `split-blocks` throws a generic "not a multiple of blockSize" error if alignment is off, which surfaces to the user as a deep-internals message. App.tsx has a friendly pre-check that fires before runSpec — keep it there so the error names the input field, not the step.
- **Adding a new (cipher, cipherMode) spec factory means updating TWO tables.** The `defaults` table in `stores/spec.ts` is the runtime source of truth (which spec actually runs); the `SUPPORTED_CIPHER_MODES_BY_CIPHER` matrix in `stores/cipher-mode.ts` is the UI source of truth (which dropdown options are enabled). If you add Phase 2's `aes-128-cbc.ts` to `defaults` but forget the matrix, the dropdown still disables CBC and the user can't pick it. If you flip the matrix but forget `defaults`, picking CBC silently falls back to single-block via `resolveDefault` — which is the exact bug that surfaced as "load-block: expected 16 got 32" in Phase 1 when a non-AES-128 cipher was paired with ECB. The regression test in `tests/cipher-mode-fallback.test.ts` will fail on the first half (matrix without defaults) and act as the canary; the second half (defaults without matrix) has no auto-detection — read the file headers in both files when adding a mode and update them together.

## Speck

- **Speck byte ordering: two conventions, neither is "wrong."** The Beaulieu et al. paper gives *word-level* test vectors only. We ship two cipher specs (`speck-32-64-be` paper-faithful, `speck-32-64-le` NSA reference) sharing the same step code; they differ only in the `byteOrder` param on each leaf. Same word-level KAT, different byte serializations. Don't quote a BE byte sequence to test an LE spec or vice versa — the codec in `src/steps/speck-word-codec.ts` is the boundary that absorbs the convention.
- **Speck's key bytes are NOT in `k_0`-first order for BE-paper.** In `K = (l_{m-2}, l_{m-3}, …, l_0, k_0)`, the visual order (and BE-paper byte order) puts `l_{m-2}` first in memory and `k_0` last. For LE-NSA it's the reverse (k_0 first). If you write a test that assumes "first 2 bytes are k_0," that's wrong for BE — `decodeKey` in the codec handles this asymmetry. Verify against the KAT before pinning intermediate-word assertions.
- **JS bitwise ops are 32-bit.** Speck's ARX kernel uses word sizes parameterized by `wordBits`. The rotations multiply by `(1 << bits) - 1` for the mask. `1 << 16 = 65536` works fine, but `1 << 32 = 1` (the shift count is taken mod 32). The `wordMask` helper special-cases 32 and uses `0xffffffff`. Larger Speck variants (Speck128/* uses 64-bit words) will need BigInt; today we only test 16-bit Speck32/64 and the code asserts up to 32.
- **Speck modular subtraction (decrypt round) can go negative in JS.** The inverse round computes `(x' XOR k) - y` which mathematically wraps mod 2^n. In JS, the `-` operator can return negative numbers; mask back to `wordBits` *after* adding `(mask + 1)` to bring the value non-negative first. Otherwise the trailing `& mask` works on a signed int32 and produces garbage for some inputs.

## Serpent

- **Serpent has two equivalent "forms" — don't mix them.** The **standard form** applies IP to the plaintext, runs 32 rounds with IP'd round keys (KHat) using per-nibble S-boxes and table-based LT, then applies FP. The **bitslice form** has no IP/FP; the same 32 rounds use non-IP'd round keys (K) with a column-wise (across-4-words) S-box and word-equation LT. Both forms produce IDENTICAL final ciphertexts. But mixing them — e.g., applying IP to the state AND using the column-wise S-box — produces a self-consistent but completely-wrong cipher that still round-trips (encrypt-then-decrypt = identity) without matching any published KAT. This implementation runs in standard form; if you ever swap the S-box or LT implementation between forms, you MUST swap both AND remove/add IP/FP and IP-on-round-keys together.
- **Serpent test vectors must be verified against an oracle, not assumed.** The "single-bit key" vectors (`key = 80…0, pt = 0, ct = ???`) appear in multiple sources with different conventions and DIFFERENT ciphertext values. Some references use MSB-first bit numbering, some LSB-first. Some apply the bitstream-to-bytes mapping with byte-reversed words. The KAT in `tests/serpent-vectors.test.ts` was pinned against `CryptoPlus.Cipher.pyserpent` (a transcription of the original Anderson/Biham/Knudsen reference) run interactively at implementation time. When extending Serpent, generate any new expected ciphertext from that reference, not from web-search quotations.
- **Serpent's key schedule S-box index is reversed AND offset.** Group `i` uses `S_{(35 - i) mod 8}` — equivalently `S_{(3 - i) mod 8}` with proper negative-modulo handling. Group 0 uses S_3, group 1 uses S_2, …, group 4 uses S_7, group 5 uses S_6, and so on. An end-to-end KAT will catch this if it's completely wrong, but the pinned `roundKey.0` and `roundKey.32` values in `tests/serpent-key-schedule.test.ts` are the primary defense — they catch the off-by-one cases where some round keys are coincidentally correct.
- **Serpent's padding selector is disabled today** (just like Speck's). The `applyPaddingScheme` overlay is hardcoded for `stateShape: "matrix4x4-bytes"`, but Serpent uses `BytesState`. `paddingLimits` returns `min: 16, max: 16` for all three Serpent variants — single block, no overflow allowance. A future block-size-aware load/store rework can unlock the overlay for both Speck and Serpent; until then, don't write tests that exercise padding through a Serpent spec.
- **Serpent's bit numbering is LSB-first within bytes.** State bit `b` = bit `(b % 8)` of byte `(b >> 3)`, where bit 0 of a byte is its LSB. So byte `0x80` has its high bit set, which is state bit 7 (not state bit 0). This matters when reading test vectors — `key = 80…0` puts a single 1 bit at state position 7, NOT position 0 or position 127. The Python reference uses the same convention; multiple online quotations of "Serpent test vectors" use other conventions and disagree on ciphertext values.

## Solid UI

- **Solid components must use `createMemo` for derived values** read multiple times in JSX. A plain function gets evaluated independently per access; that's three trace lookups per render in the worst case.
- **Solid `For` callbacks aren't reactive scopes** — a `const value = formatByte(..., props.format)` captured outside the JSX is computed once when the item is added. Inline the dynamic call into the JSX (`{formatByte(..., props.format)}`) so prop changes propagate. We've hit this in `MatrixView.tsx`: refactoring cell-value computation into a const broke the format-toggle reactivity.
- **Solid signal setters return the value they set.** Writing `export const setDirty = (v: boolean): void => setDirtySignal(v);` fails typecheck under `exactOptionalPropertyTypes` because `setDirtySignal(v)` returns `boolean`, not `void`. Wrap in a block (`(v) => { setDirtySignal(v); }`) to drop the return value. Hit this when wiring `stores/auto-rerun.ts`.
- **Don't set `display:` on the bare `.modal` rule for a native `<dialog>`.** The UA stylesheet's `dialog:not([open]) { display: none }` is what hides the closed modal; overriding with `display: flex` makes the dialog visible at ALL times, obscuring the rest of the page. Put flex layout on an inner wrapper (`.modal-inner`) and let the UA rule handle visibility. The backdrop is the native `::backdrop` pseudo, not a separate element.
- **In integration tests, click the format-toggle BUTTON; don't call `setByteFormat` directly.** The store call only updates the format signal — the App's `changeFormat` handler also re-renders the input AND key fields in place. Calling the setter alone leaves the key in the old format → the Run handler then rejects it as the wrong byte count. We hit this when wiring the PKCS#7 round-trip test.
- **`onCleanup` only works inside a reactive owner** (a component's setup body, a `createEffect`, a `createRoot`). Calling it inside an async event handler (after `await`) silently no-ops — the owner chain has already unwound by the time the handler resumes. If you need to schedule cleanup from an async handler (e.g. a `setTimeout` that should be cleared on unmount), track the handle as a closure variable in the component setup body and register ONE `onCleanup` there. Slice 7's `shareDocument` hit this with a 3-second `setShareStatus(null)` timer: the first draft put `onCleanup(() => clearTimeout(handle))` after the await; the fix tracks `shareStatusTimer` at component scope and registers cleanup once.
- **The auto-rerun effect must track EVERY user-input signal, not just `spec`.** App.tsx's `createEffect(on([spec, inputText, keyText, ivBytes], …))` re-runs the cipher when any of the four change. The original wiring tracked only `spec` (May 2026 commit), so plaintext / key / IV edits silently left the trace stale in auto-rerun mode AND failed to set the dirty flag in manual mode — no auto-rerun, no banner, no clue. If you add a new user-input source (a nonce, a salt, AEAD's additional-data field), extend the dep tuple at the same time you wire the input. Selector-driven helpers (`changeFormat` / `changeCipher` / `changePadding` / `applyDocument`) call `setInputText` / `setKeyText` as side effects, so each selector change now produces one extra debounced rerun on top of the spec-driven one; `pushSnapshot`'s dedup absorbs the duplicate. The 4-test cluster in `tests/app-auto-rerun-toggle.test.tsx` (auto + manual × plaintext + key) is the regression guard.
- **`@solidjs/testing-library` `cleanup()` doesn't dispose effects bound to module-scoped signals — they leak across tests.** Symptom in `app-auto-rerun-toggle.test.tsx`: rendering a fresh App in each test creates a new `createEffect(on([spec, …], …))`. The effect tracks the module-scoped `spec` signal, which `beforeEach`'s `__resetSpecForTests()` mutates → the previous-test's leaked effect fires, schedules a debounced setTimeout, and pushes a snapshot into the CURRENT test's history. Manifests as "history.length is 4 when I expected 1" in tests that touch history immediately after render. Two workarounds we use: (a) drain leaked timers with `await new Promise((r) => setTimeout(r, 250))` *after* the boot-run wait, before measuring; (b) `__resetHistoryForTests()` right before the user action so the assertion compares against a known-empty baseline. The IV test additionally has to dodge `MAX_HISTORY = 5` saturation (cap eviction would make `baseline + 1` equal `baseline`) — same fix. Fixing the underlying leak is out of scope; document the symptom and move on.
- **The `useX` accessor-factory pattern returns the accessor, NOT the value.** Stores in this project export accessors as `export const useReplicationEnabled = () => replicationEnabled;` (a factory that returns the signal getter). Callers must capture the accessor once at component init: `const replicate = useReplicationEnabled();` then call `replicate()` to read the boolean. Calling the factory inline in JSX — `data-open={useReplicationPanelOpen() ? "true" : "false"}` — returns the accessor *function* itself, which is always truthy, so the JSX always renders the "open" branch and signal updates from `setReplicationPanelOpen` never affect the DOM. Pattern is consistent across `view-replication.ts`, `view-density.ts`, `format.ts`, etc.; look for `const x = useX();` at the top of any component that consumes a store. Cost ~30 minutes of debugging during the graph-view polish session before the `useReplicationEnabled` / `useReplicationThreshold` sibling pattern made the mistake obvious.
- **In tests, import `setCipher` from `@/ui/stores/spec`, NOT `@/ui/stores/cipher`.** There are two functions with the same name. The cipher-store version (`stores/cipher.ts::setCipher`) only flips the cipher signal — the active spec stays whatever it was. The spec-store version (`stores/spec.ts::setCipher`, the one the UI uses) calls `buildCanonicalPair(c, cipherMode, paddingScheme)` and rebuilds both `specs.encrypt` and `specs.decrypt`. Tests that select a non-default cipher (e.g. `setCipher("serpent-128")` to test Serpent-specific UI) must use the spec-store import — otherwise `useSpecsByMode()()` still returns the AES-128 default and any per-cipher assertions silently match against the wrong spec. The Serpent S-box validation tests (Slice 2 of the cross-mode mirror plan) hit this on first iteration: the test selected `round.1.sub-bytes` after a `setCipher("serpent-128")` from `stores/cipher`, but both AES-128 and Serpent-128 happen to have a `round.1.sub-bytes` leaf — the AES leaf rendered (with its own `generic.byte-substitution@1` step type and its own `SyncInverseRow` component), and the assertion checking the Serpent tooltip received the AES tooltip instead. Bug surfaced as "Compute the inverse of this S-box and write it to every generic.byte-substitution@1 step…" failing a regex looking for "Serpent S-boxes are independent." Fix is a one-line import change; the bug is hard to spot because every other call works.

## Graph view (GraphView.tsx)

- **Replicas live on the axis ORTHOGONAL to the state spine at that scope.** Vertical-stack groups have a vertical spine; their replicas go in the LEFT gutter (horizontal axis). Horizontal flows (root + iterate body) have a horizontal spine; their replicas LIFT above the consumer (vertical axis). Putting the replica on the SAME axis as the spine obscures the spine arrow — that's the bug class the gutter/lift split exists to prevent. When you add a new layout direction or a non-linear flow (Feistel future), apply the same orthogonal-axis principle.
- **Inside a vertical-stack group, the LEFT gutter is safe only when the consumer is NOT the first non-replica child.** The incoming inter-group state spine enters at the first child's y from the left; a LEFT-gutter replica at that y would intercept it. AES's `add-round-key` is the LAST step → gutter safe. Serpent's `add-round-key` is the FIRST step → must lift the column down and place the replica above the consumer at the column x instead. The `kind === "group"` branch in `layoutNode` partitions replicas by "is consumer === firstNormalId" to pick gutter vs lift; both branches can fire in a mixed group (different replicas, different placements).
- **Pinned positions are absolute SVG coordinates.** A drag at density=normal (1.0×) saves the absolute pixel position; flipping to compact (0.75×) shrinks all the surrounding flow but the pin stays put → overlap. `setViewDensity` in `stores/view-density.ts` calls `rescaleAllPositions(newScale / oldScale)` to keep dragged blocks in their "logical slot" across density flips. If you ever add a new pin-coord source (e.g. URL share with embedded positions), rescale at the boundary.
- **Drag handler MUST clamp newX/newY ≥ 0.** Negative SVG coords fall outside the viewBox and are clipped — the block becomes invisible AND unclickable, and the bad position persists in localStorage. Users who drag a block off the top of the canvas lose it permanently without clearing storage. The `Math.max(0, ...)` clamp in the drag handler's `onMove` is the safety net; don't remove it without providing another recovery affordance.
- **The graph view has ONE sticky header wrapper, not two stacked sticky elements.** Both the density toolbar and the per-source replication-overrides panel want to stay visible while the SVG scrolls. The pre-fix version had each set its own `position: sticky` with a hardcoded `top: 32px` on the panel — a guess at the toolbar's height that drifted whenever the toolbar's content (button padding, line-height) changed, producing visible overlap. The current design wraps both in `.graph-view-sticky-header`; only the wrapper is sticky. If you add a third element to the header band, put it inside the wrapper too — don't make it sticky.
- **Cross-component drag awareness uses a module-level signal, NOT `dataTransfer.getData()`.** `dataTransfer.getData()` deliberately returns the empty string outside the `drop` event (browser security around cross-origin drags) — you cannot read the dragged step's type during `dragover` to decide whether to grey a drop anchor. `StepPalette.tsx` exports `useActiveDragStepType()` (a Solid signal flipped by `dragstart` / `dragend` on palette entries) that the `GraphView` reads via `createMemo` to derive `dragging-bytes` / `dragging-matrix` classes on `.graph-view`. CSS rules in `app.css` then dim mismatched anchors via `[data-state-shape]`. If you add a new drag source that needs the same awareness, follow the same module-signal pattern — don't try to read from `dataTransfer` outside `drop`.
- **`state-shape-mismatch` warnings are STATIC; the rest are trace-derived.** `validateGraph(graph, trace)` produces orphaned-read / unused-write / cycle warnings, all requiring a successful Run. `validateShapes(spec, registry)` runs against the spec alone — it lights up the moment an incompatible step is dropped, even before Run. `GraphView`'s `rawWarnings` memo concatenates the two. When you add a new warning kind, decide which lane it belongs in based on whether the detection needs frames or just the spec.
- **Edge bundling collapses N same-`(from, to, kind, isFeedback)` aux edges into one rendered path.** Render-time helpers keyed off `GraphEdge` reference identity (port-spreading's `slotOf`, replica-row lookups via `consumerPortOffset` / `replicaSourceXOffset`) MUST be built from the bundle's `representativeEdge`s, not from the raw `graph.edges`. Otherwise the assignment counts the N pre-bundle edges as N incoming slots — and the visual that's now one centered arrow renders offset to `slot 0 of N`, missing the consumer's midpoint. The shim in `portAssignment`'s memo (`bundles.map(b => b.representativeEdge)`) is what keeps the math honest. The other axis of subtle breakage: the bundle key includes `isFeedback`. State edges always have `isFeedback = false`; aux edges typically do too, but cross-iteration aux flows (CBC's `cbc-snapshot → cbc-xor`) have `isFeedback = true` and must NOT bundle with same-pair forward aux edges — dashed styling applies bundle-wide. Future cipher with mixed-feedback same-pair edges: the key split handles it; just don't drop `isFeedback` from the predicate "for simplicity."
- **When you change an iterate's `childIds` invariants in `expandCollapsedIterates`, you have to touch TWO downstream sites — they each special-case "consumer is iterate" independently.** First is `layoutRoot`'s replica-anchor pass (`layoutNode`'s sibling iterate-body pass too): when the replica's consumer is an iterate, the anchor x reads the iterate's *first non-replica child* so the replica lands above the first real body step rather than above the iterate's left edge. Second is the pure helper `visualEdgeTargetId`: same lookup pointed at a different concern — the rendered arrow's *target* gets retargeted from `edge.to` (the iterate) to that first body step so the arrowhead lands on the actual consumer. Both special-cases were written assuming the iterate's first non-replica child is a real body step. Option C (Box-with-header chip-row) put block chips as the iterate's `childIds`, so both sites started reading chip 0 as "the first body step" — replicas + arrow tips all converged on block 1, falsely reading as "feeds only block 1." Cost: had to ship two follow-up commits (`8f5ac60` adding the anchor-x override + `59e85de` adding the matching `visualEdgeTargetId` override) after a manual browser pass on the original Option C fix surfaced the second of them. The escape hatch is identical in both sites: if the first non-replica child has `blockChipOf !== undefined`, fall back to the iterate (center-x in layout, `edge.to` in retarget). When you next change `expandCollapsedIterates`, grep both sites first.

## URL share / CompressionStream (url-share.ts)

- **jsdom 29's `Blob` does NOT implement `.stream()`** — the idiomatic compression form `new Blob([bytes]).stream().pipeThrough(new CompressionStream(...))` works in browsers and in Node but throws `TypeError: .stream is not a function` under jsdom. Feed input through the `CompressionStream.writable.getWriter()` interface instead (writer.write(input); writer.close()), and read the output from `new Response(stream.readable).arrayBuffer()`. Production and jsdom-test paths then run identical code.
- **`CompressionStream` errors reject the writer's promises INDEPENDENTLY of the readable side.** When you feed corrupt bytes into `DecompressionStream("deflate-raw")`, both `writer.write(input)` and `writer.close()` reject, AND so does the readable consumer. Even if you `await` the readable error correctly (and surface it as a friendly user error), the writer rejections become unhandled. Attach a no-op `.catch(() => {})` to both writer promises explicitly. Without this, vitest reports an unhandled rejection per failed-decode test even though every assertion passes.
- **Pick `deflate-raw`, not `gzip`, for short payloads.** gzip wraps the deflate stream with a 10-byte header + 8-byte CRC32 footer; deflate-raw is the raw deflate bitstream. For sub-2 KB payloads (our entire size range), that ~18 bytes is a measurable fraction of the encoded length. The choice is invisible at large sizes but matters here.
- **Don't try to inject the URL-hash decode "before localStorage hydration."** The store modules' `loadInitial()` calls run at IMPORT time, well before App mounts. There's no realistic way to interpose without reorganizing the boot graph. Instead: decode on `onMount` and rely on `setSpecFromDocument` to override whatever localStorage hydrated with. A brief sub-frame of pre-mount state is acceptable.
- **Clear the hash via `replaceState`, not `pushState`.** A refresh of a `#doc=…` URL would re-apply the doc and clobber any edits the user made since the initial load. Stripping the hash on success prevents that. Use `replaceState` so the back button doesn't bounce the user to a "still has the hash" history entry — they'd just bounce right back when the next decode fires.

## Port-native primitives (Phase 2+ universal-port plan)

The port-native primitives shipped under the universal-port-dataflow plan (Slices 2.1a–2.6d so far) DO NOT follow the legacy step-types' `auxName + byteLength` pattern. Each has its own param surface — calling them with a guessed param shape produces "params.X must be Y" errors at run time. When composing a port-native cipher (SHA-256 today; SHA-3 / BLAKE2 / Poly1305 in the future), keep this table handy:

| Step type | Params | Notes |
|---|---|---|
| `rotate-bits-right@1` | `bits: number`, `wordBits: number` | NOT `shift`. NOT `byteLength` — `wordBits` (32 for SHA-256 σ₀/σ₁) implies it. |
| `shift-bits-right@1` | `bits: number`, `wordBits: number` | NOT `shift`. NOT `byteLength`. |
| `add-mod-32@1` | `inputCount: number` | NOT `byteLength` — fixed at 4 by `mod-32`. |
| `xor@1` | `inputCount: number` | NOT `byteLength` — polymorphic on input length (all inputs must agree). |
| `and@1` | `inputCount: number` | NOT `byteLength` — polymorphic. |
| `not@1` | *(empty)* | No params — unary, polymorphic on input length. |
| `concat@1` | `inputCount: number` | NOT `byteLength` — each input's length is independent; output length is the sum. |
| `byte-slice@1` | `sourceByteLength: number`, `offset: number`, `length: number` | Bracketed indexing; `sourceByteLength + offset + length` together pin the editor's slot semantics. |
| `split-bytes@1` | `widths: number[]` | NOT `count` — the lengths array IS the count (and pins each output's size). |
| `aux-load-bytes@1` | `auxName: string`, `byteLength: number` | The only port-native primitive that takes `byteLength` — it asserts the loaded aux length at run-time. |
| `generic.state-to-aux-bytes@1` | `auxName: string` | Bytes-shape sibling of `generic.state-to-aux@1`. No `byteLength` — polymorphic on state length. |

**Why the asymmetry.** Legacy step types take `byteLength` because their state shape is encoded in the param block (matrix4x4-bytes = 16, AES key sizes = 16/24/32). Port-native bitops are polymorphic — `xor@1` works on any-length operands as long as all operands agree — so a fixed `byteLength` param would be over-constrained. The four-byte add-mod-32 is the exception (and even there `inputCount` parameterises arity, not width).

**Composer-time fail mode.** The executors' `readParams` validators check the params they ARE looking for; they DON'T reject extras. So `{ type: "xor@1", params: { byteLength: 4 } }` throws `xor: params.inputCount must be a positive integer (≥ 1)` because `inputCount` is missing — not because `byteLength` was rejected. Same for `{ type: "rotate-bits-right@1", params: { shift: 7 } }` — fails with "params.bits must be …" because `bits` wasn't provided. The error message names the param the executor wanted, NOT the wrong one you supplied. Read it carefully when copy-pasting a spec node from a legacy step — what you thought was a renamed param is actually a missing one.

## Tooling / shell

- **Don't redirect native command stderr in PowerShell with `2>&1`.** PowerShell 5.1 wraps stderr lines in `NativeCommandError` records and sets `$?` to false even on success exit code 0. Capture stdout only, or merge in a different way.
