# Things to avoid (Claude tends to get these wrong)

Topic-grouped list of footguns specific to this codebase. The top-level `CLAUDE.md` summarises this file with a one-line pointer; consult the relevant section when you're about to work on that area.

## AES (FIPS-197)

- **FIPS-197 has multiple appendices with DIFFERENT keys.** Appendix B uses key `2b7e1516…`, Appendix C.1 uses `000102…0e0f`, Appendix C.2 uses a 24-byte AES-192 key. *Don't quote a value from one appendix to test a vector from another.* Verify the key matches before asserting an intermediate state.
- **SubBytes and ShiftRows commute.** Both are byte-wise permutations; swapping their order in a round produces *identical* ciphertext. This is a real algebraic property, exploited by efficient AES implementations. If you're writing a "reordering changes the output" test, swap **ShiftRows ↔ MixColumns** instead.
- **The AES state matrix is column-major.** Byte at row `r`, col `c` lives at `bytes[r + 4*c]`. The first 4 bytes of the input go into column 0 (top-to-bottom), not row 0 (left-to-right). Visualization conventions sometimes invert this.
- **GF(2^8) uses the polynomial `x^8 + x^4 + x^3 + x + 1` (0x11b).** Don't use 0x1b alone (that's the reduction-when-MSB-is-set part of `xtime`).
- **Key expansion uses the FORWARD S-box, even when decrypting.** The inverse cipher consumes the same round keys in reverse order; it does not re-derive them with the inverse S-box. Both `aes-128.ts` and `aes-128-decrypt.ts` share the same `key-expansion` step verbatim.
- **AES-256 has an extra `i % Nk == 4` SubWord-only branch in key expansion.** When `Nk > 6`, every word at `i % Nk == 4` passes through SubWord WITHOUT RotWord and WITHOUT an Rcon XOR. Only AES-256 (Nk=8) triggers it — AES-128/192 never reach the branch. If you assert only the final round key, an end-to-end KAT can pass with a wrong intermediate by coincidence. `tests/aes-256-vectors.test.ts` asserts `roundKey.3` directly (= w[12..15], where w[12] is the first index that fires the branch) as the specific guard.
- **AES key length and `rounds` must agree: `rounds === Nk + 6`.** Key-expansion asserts this — a 24-byte key with `rounds: 10` (or any mismatched pair) throws "rounds (X) must equal Nk+6 (Y)". When writing a new AES-variant spec, both the `inputs.key.byteLength` and the key-expansion `rounds` param must move together.

## Padding overlay

- **PKCS#7 always adds at least one byte of padding.** When the raw input is already a clean block multiple, canonical PKCS#7 appends a FULL extra block of `blockSize`. The single-block UI caps input at `blockSize - 1` to avoid this case; the step itself implements the canonical behavior. Don't "optimize" by skipping padding when `input.length % blockSize === 0` — you'll break unpad.
- **`applyPaddingScheme` walks the TOP level of `spec.steps` only.** The overlay step types (pkcs7-pad/unpad et al.) are always inserted at the top level so a top-level filter cleanly strips them without descending into per-round groups. If a future scheme needs to insert leaves inside groups, the helper needs a deeper walk — don't sneak overlay leaves into nested groups.
- **The overlay's `blockByteLength` param is REQUIRED and nullable — `undefined` means "no overlay".** (Phase B of `docs/plans/foamy-prancing-wren.md`.) The old AES-by-spec-id-prefix gate is gone; what scopes the overlay now is the CALLER declining to name a block width. Every call site must consciously pass a width or `undefined` — a hash, RSA, or a cipher with no `BlockCipherCore` passes `undefined` and gets its spec back canonical. Don't "helpfully" default the param to 16: that silently pads an 8-byte-block cipher to 16, producing a plausible spec that encrypts the wrong bytes. Don't make it optional either — a forgotten argument would then silently disable padding instead of failing to compile.
- **In `setPadding`, gate the width on `specs().kind === "cipher"`, not on `useCipher()()` alone.** The cipher signal keeps its last value while a hash or RSA is active ("remember last cipher"), so reading it unconditionally hands 16 to an RSA spec and splices a pad into it.
- **The overlay has ONE branch now, not three.** The matrix multi-block branch and the `[pad → load-block]` / `[store-block → unpad]` chain are gone — they served the `MatrixState` thread retired in Phase 5 Slice 5.1, along with the `split-blocks`/`concat-blocks` steps that made such a spec runnable. Every spec is port-native byte-flat, so the overlay just splices a pad into the PORT graph: prepend a pad reading `$input` and repoint the former `$input` consumers to it (encrypt), or append an unpad and move `spec.outputFrom` onto it (decrypt).

## Multi-block / iterate

- **The iterate node delegates byte slicing to step executors.** The runtime never reads `state.bytes.subarray(i*16, (i+1)*16)` itself. Instead, a `split-blocks@1` step BEFORE the iterate writes `aux["plaintext-blocks"]: MatrixState[]`, and the iterate reads from that aux array each iteration. This keeps the executor signature `(state, params, ctx) → state` intact — no special "runtime can slice bytes" carve-out for iterate. When Phase 3 lands CTR, the same pattern: a step does the work, the iterate just walks the aux array. Don't put byte-slicing logic in the runtime.
- **Per-iteration step ids get a `:b{i}` suffix automatically.** A `round.1.sub-bytes` leaf inside an iterate emits `round.1.sub-bytes:b0`, `round.1.sub-bytes:b1`, … per iteration. The trace store's `setTrace` is stepId-anchored, so this is what makes "preserve focus across re-runs" work on a multi-block trace. Don't write step ids with literal `:b` substrings in them — they'd collide with the suffix convention. The runtime also stamps `frame.blockIndex` so renderers (`BlockBadge`) can show context without parsing the stepId.
- **`paddingLimits` got a fourth `cipherMode` arg with a default.** Existing call sites that don't pass it get `cipherMode = "single-block"` and behave identically to before — same ranges, same scheme-specific caps. The new arg is what widens the range for multi-block up to `MAX_BLOCKS_UI × blockByteLength`. If you add a new call site in code that's mode-aware, plumb the cipherMode through; if you're calling from a single-block test, the default is the right answer.
- **`paddingLimits` keeps a per-cipher `switch` (`singleBlockLimits`) as a FALLBACK, and that is not dead weight.** It answers "one block is how many bytes?" for ciphers with no `BlockCipherCore` — which is every cipher but AES today. "`core.blockByteLength` replaces the switch outright" only becomes true once EVERY cipher has a core; until then it shrinks one entry per core landed. Don't add a parallel `BLOCK_BYTES_BY_CIPHER` table — it would drift against `SUPPORTED_CIPHER_MODES_BY_CIPHER` and claim authority the cores actually hold. Enumerating `Cipher` in a UI store is CORRECT; the anti-pattern is only in `src/ciphers/` mode builders.
- **Run handler's alignment check belongs in App.tsx, not deep in the runtime.** Multi-block decrypt + multi-block encrypt-with-`none` both require input length `% blockByteLength == 0`. The iterate's block split throws a generic error if alignment is off, which surfaces to the user as a deep-internals message. App.tsx has a friendly pre-check that fires before runSpec — keep it there so the error names the input field, not the step.
- **"Additive optional field, no `schemaVersion` bump" is a claim about the TYPE — persistence is a SEPARATE obligation, and Zod fails it silently.** `document-schema.ts` deep-validates the spec tree and **strips keys it does not declare**, so a new `IterateGroup`/`StepGroup` field that isn't added there round-trips to `undefined` on every Save/Load and URL-share. `allowPartialFinalBlock` shipped this way for an hour: the type was additive, the runtime honoured it, every KAT passed — and a shared CTR link would have reopened with the flag gone, silently rejecting the very partial input it was built to demonstrate. No error, no visual tell. The schema's own comments beside `seedInput`/`chainInput`/`chainOutput` call this out (`cipherConstants` hit it in Slice A1), but nothing *enforces* it. **Whenever you add a field to a spec node, grep `document-schema.ts` for a sibling field and add yours beside it, then pin it with a round-trip test.** Step *types* need no such care — `StepLeafSchema.type` is a plain `z.string()`.
- **`allowPartialFinalBlock` is CTR-only, and disengaging padding for it took FIVE sites that must move together.** The optional `IterateGroup` flag relaxes the block-multiple throw to `ceil` and hands the final iteration a SHORT `in` block. Absent ⇒ byte-identical old behaviour, so ECB/CBC are unaffected — but the flag alone does nothing useful, because four *other* mechanisms would still force whole blocks: `App.tsx`'s `needsAlignment`, `paddingLimits`' bounds, the `requiresPadding` prose, and — the one most likely to be missed — `buildCanonicalPair` in `stores/spec.ts`, which passes `blockBytes` for every mode and would splice a pad into CTR. A surviving pad step **silently** re-fills the last block and the partial path never runs, so the feature looks implemented and does nothing. Pass `undefined` there for CTR and let `overlayApplies`' existing "no block width ⇒ no overlay" semantics do it, rather than adding a second gate inside `applyPaddingScheme`. Also: relax **both directions** — CTR ciphertext is exactly as ragged as its plaintext, so a decrypt-side alignment check rejects a short ciphertext before the runtime ever sees it.
- **When you relax a width rule, the trim must go where the SHORT value is — inside the body, not at the output.** Because the relaxed iterate shortens `in`, CTR's `ctr-trim` trims the *keystream* down to the message block between the cipher and the XOR. Trimming the final concatenated output instead is a different design, and a worse one pedagogically: it requires zero-padding the message first, which makes a fake plaintext block visibly enter the XOR and contradicts the very claim ("CTR needs no padding") the feature exists to demonstrate. The core stays untouched throughout because CTR's counter rides `chain` (always full width `B`), not `in`.
- **Adding a new (cipher, cipherMode) spec means updating THREE tables.** `BLOCK_CIPHER_CORES` in `stores/block-cipher-cores.ts` is the capability source of truth (a cipher CANNOT run a mode without a core); the `defaults` table in `stores/spec.ts` is the runtime source of truth (which spec actually runs); `SUPPORTED_CIPHER_MODES_BY_CIPHER` in `stores/cipher-mode.ts` is the UI source of truth (which dropdown options are enabled). Flip the matrix but forget `defaults` and picking CBC silently falls back to single-block via `resolveDefault`. `tests/cipher-mode-fallback.test.ts` is the canary and asserts all three agree — including an explicit "core presence ⟺ multi-block support" invariant, so a matrix row without a core fails there.
- **Generalizing a hardcoded constant proves nothing while every caller still passes the old value.** Phase B replaced five `16`s with `core.blockByteLength`, but AES's block IS 16 — a stray `16` or an off-by-one would have passed the entire suite, and AES-192/256 doesn't help (also 16-byte). `tests/block-size-generic-modes.test.ts` supplies the missing value with a **fake `BlockCipherCore` carrying an 8-byte block**. If you generalize a constant, feed the generic path a value the app can't yet produce — don't wait for the real consumer. (Phase C's Blowfish core is the real consumer, and it found a bug the fake core couldn't — see the IV entry below.)
- **A persisted user input that depends on the active cipher goes stale when the cipher changes — and the store can't notice.** The IV must be exactly one block wide, but `stores/iv.ts` is module-scope with no notion of which cipher is live, and the IV is persisted while `cipher`/`cipherMode` are session-only. Phase B made the width a *parameter* (`setIvBytes(bytes, width)`) and still shipped this bug: landing on Blowfish CBC displayed the 16-byte AES default in a field that validates at 8 — **a value the field itself would reject.** `reconcileIvWidth(blockByteLength)` fixes it, called from BOTH `changeCipher` and the cipher-mode `onChange`. **Two traps if you touch this:** (1) a cipher-change-only hook MISSES the mode trigger — land on Blowfish in single-block (IV inert), flip to CBC, no cipher change fires; (2) don't do it in a global `createEffect`, which can clobber the IV `applyDocument` just restored (`spec.ts` restores a document IV with no width arg, deliberately). The drift runs BOTH ways: an 8-byte IV from a Blowfish session survives a reload onto AES + CBC.
- **A wrong-width IV cannot be caught by a KAT — the coercion is invariant.** The 16-byte default `000102…0f` truncated to 8 by the runtime's port-length coercion is `0001020304050607`, byte-identical to the correct 8-byte default. Blowfish CBC produces the *same ciphertext* broken and fixed. Pin the stored/displayed VALUE instead (`tests/iv-width-reconcile.test.ts`), and the sharpest form is "the reconciled IV is one `setIvBytes` ACCEPTS at that width". Generally: when the bug is a wrong input that coerces to the right one, the output is not the evidence.
- **The padding overlay's repoint walks container `seedInput`, not just leaf `portInputs` — despite the name.** `rewriteAllPortInputs` handles both (see its `rewriteNode`), which matters because the `$input` consumer lives in different places per spec: AES single-block's is a leaf `portInputs` binding, but Blowfish single-block's round 1 is a port-mode `group` seeded via `seedInput` with no leaf referencing `$input` at all. A portInputs-only rewrite would splice a pad that nothing consumes — and it would NOT throw: `split-bytes` coerces a short input (warn-and-run), so the body would encrypt raw unpadded bytes and the run would SUCCEED with wrong output. Any test for the overlay must assert output bytes, never `params.blockSize`.

## Speck

- **Speck byte ordering: two conventions, neither is "wrong."** The Beaulieu et al. paper gives *word-level* test vectors only. We ship two cipher specs (`speck-32-64-be` paper-faithful, `speck-32-64-le` NSA reference) sharing the same step code; they differ only in the `byteOrder` param on each leaf. Same word-level KAT, different byte serializations. Don't quote a BE byte sequence to test an LE spec or vice versa — the codec in `src/steps/speck-word-codec.ts` is the boundary that absorbs the convention.
- **Speck's key bytes are NOT in `k_0`-first order for BE-paper.** In `K = (l_{m-2}, l_{m-3}, …, l_0, k_0)`, the visual order (and BE-paper byte order) puts `l_{m-2}` first in memory and `k_0` last. For LE-NSA it's the reverse (k_0 first). If you write a test that assumes "first 2 bytes are k_0," that's wrong for BE — `decodeKey` in the codec handles this asymmetry. Verify against the KAT before pinning intermediate-word assertions.
- **JS bitwise ops are 32-bit.** Speck's ARX kernel uses word sizes parameterized by `wordBits`. The rotations multiply by `(1 << bits) - 1` for the mask. `1 << 16 = 65536` works fine, but `1 << 32 = 1` (the shift count is taken mod 32). The `wordMask` helper special-cases 32 and uses `0xffffffff`. Larger Speck variants (Speck128/* uses 64-bit words) will need BigInt; today we only test 16-bit Speck32/64 and the code asserts up to 32.
- **Speck modular subtraction (decrypt round) can go negative in JS.** The inverse round computes `(x' XOR k) - y` which mathematically wraps mod 2^n. In JS, the `-` operator can return negative numbers; mask back to `wordBits` *after* adding `(mask + 1)` to bring the value non-negative first. Otherwise the trailing `& mask` works on a signed int32 and produces garbage for some inputs.

## Serpent

- **Serpent has two equivalent "forms" — don't mix them.** The **standard form** applies IP to the plaintext, runs 32 rounds with IP'd round keys (KHat) using per-nibble S-boxes and table-based LT, then applies FP. The **bitslice form** has no IP/FP; the same 32 rounds use non-IP'd round keys (K) with a column-wise (across-4-words) S-box and word-equation LT. Both forms produce IDENTICAL final ciphertexts. But mixing them — e.g., applying IP to the state AND using the column-wise S-box — produces a self-consistent but completely-wrong cipher that still round-trips (encrypt-then-decrypt = identity) without matching any published KAT. This implementation runs in standard form; if you ever swap the S-box or LT implementation between forms, you MUST swap both AND remove/add IP/FP and IP-on-round-keys together.
- **Serpent test vectors must be verified against an oracle, not assumed.** The "single-bit key" vectors (`key = 80…0, pt = 0, ct = ???`) appear in multiple sources with different conventions and DIFFERENT ciphertext values. Some references use MSB-first bit numbering, some LSB-first. Some apply the bitstream-to-bytes mapping with byte-reversed words. The KAT in `tests/serpent-vectors.test.ts` was pinned against `CryptoPlus.Cipher.pyserpent` (a transcription of the original Anderson/Biham/Knudsen reference) run interactively at implementation time. When extending Serpent, generate any new expected ciphertext from that reference, not from web-search quotations.
- **Serpent's key schedule S-box index is reversed AND offset.** Group `i` uses `S_{(35 - i) mod 8}` — equivalently `S_{(3 - i) mod 8}` with proper negative-modulo handling. Group 0 uses S_3, group 1 uses S_2, …, group 4 uses S_7, group 5 uses S_6, and so on. An end-to-end KAT will catch this if it's completely wrong, but the pinned `roundKey.0` and `roundKey.32` values in `tests/serpent-key-schedule.test.ts` are the primary defense — they catch the off-by-one cases where some round keys are coincidentally correct.
- **Serpent's padding selector is disabled today** (just like Speck's). The `applyPaddingScheme` overlay is hardcoded for `stateShape: "matrix4x4-bytes"`, but Serpent uses `BytesState`. `paddingLimits` returns `min: 16, max: 16` for all three Serpent variants — single block, no overflow allowance. A future block-size-aware load/store rework can unlock the overlay for both Speck and Serpent; until then, don't write tests that exercise padding through a Serpent spec.
- **Serpent's bit numbering is LSB-first within bytes.** State bit `b` = bit `(b % 8)` of byte `(b >> 3)`, where bit 0 of a byte is its LSB. So byte `0x80` has its high bit set, which is state bit 7 (not state bit 0). This matters when reading test vectors — `key = 80…0` puts a single 1 bit at state position 7, NOT position 0 or position 127. The Python reference uses the same convention; multiple online quotations of "Serpent test vectors" use other conventions and disagree on ciphertext values.

## Solid UI

- **Solid components must use `createMemo` for derived values** read multiple times in JSX. A plain function gets evaluated independently per access; that's three trace lookups per render in the worst case.
- **`createMemo` evaluates EAGERLY on creation, so memo declaration ORDER matters — a memo whose body reads a `const`-declared memo defined LATER throws a TDZ `ReferenceError` ("Cannot access 'X' before initialization").** Solid runs a memo's computation immediately when `createMemo(...)` returns (to seed its value + dependency graph), not lazily on first JSX read. So if `portArrivalPoints` (early) calls `feistelCarryKeys()` (declared 150 lines later), the eager run hits the still-uninitialized `const`. Fix = move the referenced memo ABOVE its reader (its own deps must still precede it). This bit the 2026-07-12 Feistel-swap-dot work; typecheck is silent, only a browser/jsdom render surfaces it (blank canvas + `pageerror`). When adding a memo that reads another, check it's declared earlier.
- **Solid `For` callbacks aren't reactive scopes** — a `const value = formatByte(..., props.format)` captured outside the JSX is computed once when the item is added. Inline the dynamic call into the JSX (`{formatByte(..., props.format)}`) so prop changes propagate. We've hit this in `MatrixView.tsx`: refactoring cell-value computation into a const broke the format-toggle reactivity.
- **Solid signal setters return the value they set.** Writing `export const setDirty = (v: boolean): void => setDirtySignal(v);` fails typecheck under `exactOptionalPropertyTypes` because `setDirtySignal(v)` returns `boolean`, not `void`. Wrap in a block (`(v) => { setDirtySignal(v); }`) to drop the return value. Hit this when wiring `stores/auto-rerun.ts`.
- **Don't set `display:` on the bare `.modal` rule for a native `<dialog>`.** The UA stylesheet's `dialog:not([open]) { display: none }` is what hides the closed modal; overriding with `display: flex` makes the dialog visible at ALL times, obscuring the rest of the page. Put flex layout on an inner wrapper (`.modal-inner`) and let the UA rule handle visibility. The backdrop is the native `::backdrop` pseudo, not a separate element.
- **In integration tests, click the format-toggle BUTTON; don't call `setByteFormat` directly.** The store call only updates the format signal — the App's `changeFormat` handler also re-renders the input AND key fields in place. Calling the setter alone leaves the key in the old format → the Run handler then rejects it as the wrong byte count. We hit this when wiring the PKCS#7 round-trip test.
- **`onCleanup` only works inside a reactive owner** (a component's setup body, a `createEffect`, a `createRoot`). Calling it inside an async event handler (after `await`) silently no-ops — the owner chain has already unwound by the time the handler resumes. If you need to schedule cleanup from an async handler (e.g. a `setTimeout` that should be cleared on unmount), track the handle as a closure variable in the component setup body and register ONE `onCleanup` there. Slice 7's `shareDocument` hit this with a 3-second `setShareStatus(null)` timer: the first draft put `onCleanup(() => clearTimeout(handle))` after the await; the fix tracks `shareStatusTimer` at component scope and registers cleanup once.
- **The auto-rerun effect must track EVERY user-input signal, not just `spec`.** App.tsx's `createEffect(on([spec, inputText, keyText, ivBytes], …))` re-runs the cipher when any of the four change. The original wiring tracked only `spec` (May 2026 commit), so plaintext / key / IV edits silently left the trace stale in auto-rerun mode AND failed to set the dirty flag in manual mode — no auto-rerun, no banner, no clue. If you add a new user-input source (a nonce, a salt, AEAD's additional-data field), extend the dep tuple at the same time you wire the input. Selector-driven helpers (`changeFormat` / `changeCipher` / `changePadding` / `applyDocument`) call `setInputText` / `setKeyText` as side effects, so each selector change now produces one extra debounced rerun on top of the spec-driven one; `pushSnapshot`'s dedup absorbs the duplicate. The 4-test cluster in `tests/app-auto-rerun-toggle.test.tsx` (auto + manual × plaintext + key) is the regression guard.
- **`@solidjs/testing-library` `cleanup()` doesn't dispose effects bound to module-scoped signals — they leak across tests.** Symptom in `app-auto-rerun-toggle.test.tsx`: rendering a fresh App in each test creates a new `createEffect(on([spec, …], …))`. The effect tracks the module-scoped `spec` signal, which `beforeEach`'s `__resetSpecForTests()` mutates → the previous-test's leaked effect fires, schedules a debounced setTimeout, and pushes a snapshot into the CURRENT test's history. Manifests as "history.length is 4 when I expected 1" in tests that touch history immediately after render. Two workarounds we use: (a) drain leaked timers with `await new Promise((r) => setTimeout(r, 250))` *after* the boot-run wait, before measuring; (b) `__resetHistoryForTests()` right before the user action so the assertion compares against a known-empty baseline. The IV test additionally has to dodge `MAX_HISTORY = 5` saturation (cap eviction would make `baseline + 1` equal `baseline`) — same fix. Fixing the underlying leak is out of scope; document the symptom and move on.
- **The `useX` accessor-factory pattern returns the accessor, NOT the value.** Stores in this project export accessors as `export const useReplicationEnabled = () => replicationEnabled;` (a factory that returns the signal getter). Callers must capture the accessor once at component init: `const replicate = useReplicationEnabled();` then call `replicate()` to read the boolean. Calling the factory inline in JSX — `data-open={useReplicationPanelOpen() ? "true" : "false"}` — returns the accessor *function* itself, which is always truthy, so the JSX always renders the "open" branch and signal updates from `setReplicationPanelOpen` never affect the DOM. Pattern is consistent across `view-replication.ts`, `view-density.ts`, `format.ts`, etc.; look for `const x = useX();` at the top of any component that consumes a store. Cost ~30 minutes of debugging during the graph-view polish session before the `useReplicationEnabled` / `useReplicationThreshold` sibling pattern made the mistake obvious.
- **In tests, import `setCipher` from `@/ui/stores/spec`, NOT `@/ui/stores/cipher`.** There are two functions with the same name. The cipher-store version (`stores/cipher.ts::setCipher`) only flips the cipher signal — the active spec stays whatever it was. The spec-store version (`stores/spec.ts::setCipher`, the one the UI uses) calls `buildCanonicalPair(c, cipherMode, paddingScheme)` and rebuilds both `specs.encrypt` and `specs.decrypt`. Tests that select a non-default cipher (e.g. `setCipher("serpent-128")` to test Serpent-specific UI) must use the spec-store import — otherwise `useSpecsByMode()()` still returns the AES-128 default and any per-cipher assertions silently match against the wrong spec. The Serpent S-box validation tests (Slice 2 of the cross-mode mirror plan) hit this on first iteration: the test selected `round.1.sub-bytes` after a `setCipher("serpent-128")` from `stores/cipher`, but both AES-128 and Serpent-128 happen to have a `round.1.sub-bytes` leaf — the AES leaf rendered (with its own `generic.byte-substitution@1` step type and its own `SyncInverseRow` component), and the assertion checking the Serpent tooltip received the AES tooltip instead. Bug surfaced as "Compute the inverse of this S-box and write it to every generic.byte-substitution@1 step…" failing a regex looking for "Serpent S-boxes are independent." Fix is a one-line import change; the bug is hard to spot because every other call works.

- **A palette-dropped leaf has `params: {}`, so a ParamEditor row gated on a value being PRESENT can never be used.** `insertStepIntoSpec` creates the new leaf with empty params by design — the user is supposed to fill them in. An editor row written as `<Show when={params().d !== undefined}>` therefore renders for a leaf that already has a `d` and vanishes for the freshly dropped one that needs it, leaving the step permanently unconfigurable from the UI. **Key every row on the step TYPE instead.** Two things hide this: `tests/param-editor-coverage.test.tsx` walks only step types appearing in a SHIPPED spec, so a palette-only family is out of its scope entirely; and rendering a hand-built leaf with populated params passes while the real user path stays broken. Test through `insertStepIntoSpec` (see `tests/zq-param-editor-coverage.test.tsx`), and add a mirror assertion so the fix cannot degrade into "always show every row".

## Graph view (GraphView.tsx)

- **Replicas live on the axis ORTHOGONAL to the state spine at that scope.** Vertical-stack groups have a vertical spine; their replicas go in the LEFT gutter (horizontal axis). Horizontal flows (root + iterate body) have a horizontal spine; their replicas LIFT above the consumer (vertical axis). Putting the replica on the SAME axis as the spine obscures the spine arrow — that's the bug class the gutter/lift split exists to prevent. When you add a new layout direction or a non-linear flow (Feistel future), apply the same orthogonal-axis principle.
- **Inside a vertical-stack group, the LEFT gutter is safe only when the consumer is NOT the first non-replica child.** The incoming inter-group state spine enters at the first child's y from the left; a LEFT-gutter replica at that y would intercept it. AES's `add-round-key` is the LAST step → gutter safe. Serpent's `add-round-key` is the FIRST step → must lift the column down and place the replica above the consumer at the column x instead. The `kind === "group"` branch in `layoutNode` partitions replicas by "is consumer === firstNormalId" to pick gutter vs lift; both branches can fire in a mixed group (different replicas, different placements).
- **Pinned positions are absolute SVG coordinates.** A drag at density=normal (1.0×) saves the absolute pixel position; flipping to compact (0.75×) shrinks all the surrounding flow but the pin stays put → overlap. `setViewDensity` in `stores/view-density.ts` calls `rescaleAllPositions(newScale / oldScale)` to keep dragged blocks in their "logical slot" across density flips. If you ever add a new pin-coord source (e.g. URL share with embedded positions), rescale at the boundary.
- **Drag handler MUST clamp newX/newY ≥ 0.** Negative SVG coords fall outside the viewBox and are clipped — the block becomes invisible AND unclickable, and the bad position persists in localStorage. Users who drag a block off the top of the canvas lose it permanently without clearing storage. The `Math.max(0, ...)` clamp in the drag handler's `onMove` is the safety net; don't remove it without providing another recovery affordance.
- **The graph view has ONE sticky header wrapper, not two stacked sticky elements.** Both the density toolbar and the per-source replication-overrides panel want to stay visible while the SVG scrolls. The pre-fix version had each set its own `position: sticky` with a hardcoded `top: 32px` on the panel — a guess at the toolbar's height that drifted whenever the toolbar's content (button padding, line-height) changed, producing visible overlap. - **Edge bundling collapses N same-`(from, to, kind, isFeedback)` aux edges into one rendered path.** Render-time helpers keyed off `GraphEdge` reference identity (port-spreading's `slotOf`, replica-row lookups via `consumerPortOffset` / `replicaSourceXOffset`) MUST be built from the bundle's `representativeEdge`s, not from the raw `graph.edges`. The shim in `portAssignment`'s memo (`bundles.map(b => b.representativeEdge)`) is what keeps the math honest. The other axis of subtle breakage: the bundle key includes `isFeedback`. State edges always have `isFeedback = false`; aux edges typically do too, but cross-iteration aux flows (CBC's `cbc-snapshot → cbc-xor`) have `isFeedback = true` and must NOT bundle with same-pair forward aux edges — dashed styling applies bundle-wide. Future cipher with mixed-feedback same-pair edges: the key split handles it; just don't drop `isFeedback` from the predicate "for simplicity."
- **When you change an iterate's `childIds` invariants in `expandCollapsedIterates`, you have to touch TWO downstream sites — they each special-case "consumer is iterate" independently.** First is `layoutRoot`'s replica-anchor pass (`layoutNode`'s sibling iterate-body pass too): when the replica's consumer is an iterate, the anchor x reads the iterate's *first non-replica child* so the replica lands above the first real body step rather than above the iterate's left edge. Both special-cases were written assuming the iterate's first non-replica child is a real body step. Cost: had to ship two follow-up commits (`8f5ac60` adding the anchor-x override + `59e85de` adding the matching `visualEdgeTargetId` override) after a manual browser pass on the original Option C fix surfaced the second of them. The escape hatch is identical in both sites: if the first non-replica child has `blockChipOf !== undefined`, fall back to the iterate (center-x in layout, `edge.to` in retarget). When you next change `expandCollapsedIterates`, grep both sites first.
- **Drag-to-pan only starts on a passive canvas surface — `target === wrapper`, the SVG root, OR a `graph-container-rect` (the body of a container).** The pan handler (`handleCanvasPanPointerDown`, on the `.graph-view` wrapper) bails on any other target so it never steals a node/edge/header gesture. - **A `GraphView` value lookup for a port-flow edge between MULTI-PORT leaves needs the edge's `fromPort`/`toPort`, not just `framePrimaryOut/InBytes`.** Those helpers resolve only the `"state"` port or the *sole* port; a `split-bytes@1` (outputs `output0`/`output1`) or a fan-in `xor`/`concat` (multiple inputs) returns `null`, so a `split → fxor` / `split → recombine` edge can't be read from the `(from, to)` pair alone — you need to know *which* port. `inferPortEdges` stamps every port-flow `GraphEdge` with `fromPort` (producer output) and `toPort` (consumer input = the `portInputs` binding key); `lookupRegularState` reads them as a fallback *after* the primary helpers (so single-port edges stay byte-identical). `toPort` is the reliable read (always a real input port); `fromPort` may be a container pseudo-port (`"in"`/`"out"`/`"chain"`) after seedInput/bodyOutput resolution, so it's secondary. The NODE lookup falls back to a leaf's primary *input* for a multi-output leaf (clicking `split` shows the block it divides). These fields are optional — don't add them to `encodeEdgeKey` (from/to/auxKey/kind), and don't assume they're present on aux edges or container-targeted loop-input edges.
- **Any graph-rewrite stage that REBUILDS edges must copy `fromPort`/`toPort` forward — and value-lookup tests must run the FULL pipeline, not raw `deriveAuxGraph`.** The UI runs `deriveAuxGraph → collapseGraph → replicateHighFanoutSources`, and the latter two reconstruct `GraphEdge` objects from scratch. ""}`, where `keptToPort` is dropped when the endpoint remaps into a collapsed container, so a container-level merge still collapses correctly); (2) `bundleEdges` (via `bundleKeyFor` — so the rails render as two arrows, not one `×2` state bundle, which would route clicks to the bundle-summary path whose two `"port-flow"` auxKeys carry no frame → "no frame found for either endpoint of state edge"); (3) `encodeEdgeKey`/`decodeEdgeKey` (5-part `from|to|auxKey|kind|toPort`, back-compat with the legacy 4-part form) so the two rails get DISTINCT inspector keys; (4) `GraphView`'s `portArrivalPoints` memo (also via `bundleKeyFor`) — the 4th site, which for a while kept its OWN `(from,to,kind,fb)`-only lookup map and so collided the per-port bundles, stacking every port's arrival dot on ONE arrowhead (the 2026-07-12 RSA multi-port-dot bug). That divergence is why (2) and (4) now share the exported `bundleKeyFor`: any NEW code mapping an edge back to "which rendered arrow is this?" MUST call it, not hand-roll the key. Aux edges carry no `toPort`, so every site is byte-identical to before for them (the `×N` round-key pill still bundles). Guards: `tests/graph-port-edge-derivation.test.ts` (dedup survives + re-merges), `tests/graph-bundle.test.ts` (`bundleKeyFor` keys port-flow by `toPort`; aux fan-in shares one key), `tests/graph-view-rsa.test.tsx` (`square-0`'s a/b render two "arrived" dots at distinct coords).

## URL share / CompressionStream (url-share.ts)

- **jsdom 29's `Blob` does NOT implement `.stream()`** — the idiomatic compression form `new Blob([bytes]).stream().pipeThrough(new CompressionStream(...))` works in browsers and in Node but throws `TypeError: .stream is not a function` under jsdom. Feed input through the `CompressionStream.writable.getWriter()` interface instead (writer.write(input); writer.close()), and read the output from `new Response(stream.readable).arrayBuffer()`. Production and jsdom-test paths then run identical code.
- **`CompressionStream` errors reject the writer's promises INDEPENDENTLY of the readable side.** When you feed corrupt bytes into `DecompressionStream("deflate-raw")`, both `writer.write(input)` and `writer.close()` reject, AND so does the readable consumer. Even if you `await` the readable error correctly (and surface it as a friendly user error), the writer rejections become unhandled. Attach a no-op `.catch(() => {})` to both writer promises explicitly. Without this, vitest reports an unhandled rejection per failed-decode test even though every assertion passes.
- **Pick `deflate-raw`, not `gzip`, for short payloads.** gzip wraps the deflate stream with a 10-byte header + 8-byte CRC32 footer; deflate-raw is the raw deflate bitstream. For sub-2 KB payloads (our entire size range), that ~18 bytes is a measurable fraction of the encoded length. The choice is invisible at large sizes but matters here.
- **Don't try to inject the URL-hash decode "before localStorage hydration."** The store modules' `loadInitial()` calls run at IMPORT time, well before App mounts. There's no realistic way to interpose without reorganizing the boot graph. Instead: decode on `onMount` and rely on `setSpecFromDocument` to override whatever localStorage hydrated with. A brief sub-frame of pre-mount state is acceptable.
- **Clear the hash via `replaceState`, not `pushState`.** A refresh of a `#doc=…` URL would re-apply the doc and clobber any edits the user made since the initial load. Stripping the hash on success prevents that. Use `replaceState` so the back button doesn't bounce the user to a "still has the hash" history entry — they'd just bounce right back when the next decode fires.

## Port-native primitives (Phase 2+ universal-port plan)

- **A step whose port contract is FUNCTION-FORM must have every param it reads added to `KITCHEN_SINK`** in `tests/byte-native-ports-contract.test.ts`. That test resolves each function-form contract against one shared params object; a param it does not carry makes the contract throw, and the failure says only "ported steps whose contract threw — extend KITCHEN_SINK with the missing param(s)" plus the step type. It names neither the param nor the reason, and it fires nowhere near the file you were editing. Static (`Map`) contracts are exempt, which is why the trap only springs on the steps that derive a port width from a param — `zq-vec-mul-scalar@1` (`scalar` from `coeffBytes`) and `ml-kem.prf@1` (`output` = 64η) have both hit it.

The port-native primitives shipped under the universal-port-dataflow plan (Slices 2.1a–2.6d so far) DO NOT follow the legacy step-types' `auxName + byteLength` pattern. Each has its own param surface — calling them with a guessed param shape produces "params.X must be Y" errors at run time. When composing a port-native cipher (SHA-256 today; SHA-3 / BLAKE2 / Poly1305 in the future), keep this table handy:

| Step type | Params | Notes |
|---|---|---|
| `rotate-bits-right@1` | `bits: number`, `wordBits: number` | NOT `shift`. NOT `byteLength` — `wordBits` (32 for SHA-256 σ₀/σ₁) implies it. |
| `shift-bits-right@1` | `bits: number`, `wordBits: number` | NOT `shift`. NOT `byteLength`. |
| `add-mod-32@1` | `inputCount: number` | NOT `byteLength` — fixed at 4 by `mod-32`. |
| `xor@1` | `inputCount: number` | NOT `byteLength` — polymorphic on input length (all inputs must agree). |
| `and@1` | `inputCount: number` | NOT `byteLength` — polymorphic. |
| `not@1` | *(empty)* | No params — unary, polymorphic on input length. |
| `concat@1` | `inputCount: number` | NOT `byteLength` — each input's length is independent; output length is the sum. |
| `byte-slice@1` | `sourceByteLength: number`, `offset: number`, `length: number` | Bracketed indexing; `sourceByteLength + offset + length` together pin the editor's slot semantics. |
| `split-bytes@1` | `widths: number[]` | NOT `count` — the lengths array IS the count (and pins each output's size). |
| `aux-load-bytes@1` | `auxName: string`, `byteLength: number` | The only port-native primitive that takes `byteLength` — it asserts the loaded aux length at run-time. |
| `generic.state-to-aux-bytes@1` | `auxName: string` | Bytes-shape sibling of `generic.state-to-aux@1`. No `byteLength` — polymorphic on state length. |
| `rotate-lanes@1` | `wordBits: number`, `offsets: number[]`, `littleEndian?: boolean` | Keccak ρ. Per-lane **left** rotation (`offsets.length` MUST equal `input.length / (wordBits/8)`). `littleEndian: true` for Keccak — see the SHA-3 section below. |
| `keccak.theta@1` | *(empty)* | Keccak θ. Fixed 5×5×64 geometry (200-byte state); no params. |
| `keccak.iota@1` | `round: number`, `auxName?: string` | Keccak ι. Reads `aux[auxName ?? "RC"]` via `meta.auxReadPorts`; set `auxName` explicitly so the constants panel attributes the reader. |
| `keccak.pad@1` | `rate: number`, `domainByte: number` | pad10\*1 + domain byte (`0x06` SHA-3, `0x1F` SHAKE, `0x04` cSHAKE/KMAC). NOT `pad-with-byte@1` + length suffix — the sponge has no length field. |
| `encode-string@1` | *(empty)* | SP 800-185 `encode_string(S) = left_encode(8·len(S)) ‖ S`. Length read at run time; the prefix is the **BIT** length — see the cSHAKE/KMAC section. |
| `bytepad@1` | `w: number` | SP 800-185 `bytepad(X, w) = left_encode(w) ‖ X ‖ 0…0` up to a multiple of `w` bytes (`w` = the sponge rate). |
| `right-encode@1` | `value: number` | SP 800-185 `right_encode(value)` (count byte last). KMAC passes `outputBytes·8`; KMACXOF passes `0`. Zero inputs. |

**Why the asymmetry.** Legacy step types take `byteLength` because their state shape is encoded in the param block (matrix4x4-bytes = 16, AES key sizes = 16/24/32). Port-native bitops are polymorphic — `xor@1` works on any-length operands as long as all operands agree — so a fixed `byteLength` param would be over-constrained. The four-byte add-mod-32 is the exception (and even there `inputCount` parameterises arity, not width).

**Composer-time fail mode.** The executors' `readParams` validators check the params they ARE looking for; they DON'T reject extras. So `{ type: "xor@1", params: { byteLength: 4 } }` throws `xor: params.inputCount must be a positive integer (≥ 1)` because `inputCount` is missing — not because `byteLength` was rejected. Same for `{ type: "rotate-bits-right@1", params: { shift: 7 } }` — fails with "params.bits must be …" because `bits` wasn't provided. The error message names the param the executor wanted, NOT the wrong one you supplied. Read it carefully when copy-pasting a spec node from a legacy step — what you thought was a renamed param is actually a missing one.

## SHA-3 / Keccak (FIPS 202)

- **Keccak lanes are LITTLE-endian; the SHA-256 template is big-endian.** This is the #1 SHA-3 KAT footgun — it passes every structural/shape check and silently produces a **wrong digest**. Keccak's 200-byte state is a little-endian bit string (FIPS 202 §3.1.2). `rotate-bits-right@1` assembles its 64-bit word **big-endian** (`decodeBE64`/`encodeBE64`), so feeding it a raw Keccak lane rotates the wrong bits and scrambles ρ. The fix shipped here: keep the state in standard LE byte-string form throughout and do the only endianness-sensitive math (ρ's rotation, θ's internal rotate-by-1) *inside* LE-aware steps (`rotate-lanes@1` with `littleEndian: true`, and `keccak.theta@1`). Net: **`rotate-bits-right@1` is never used for Keccak**, and there is no boundary byte-reversal. If you add SHAKE / SHA3-224/384/512, reuse `rotate-lanes@1` — do not reach for `rotate-bits-right@1`.
- **ρ is a LEFT rotate with 25 DISTINCT per-lane offsets.** `rotate-bits-right@1` rotates every word by the *same* amount (and rightward), so ρ cannot be one such leaf — that's why `rotate-lanes@1` exists (per-lane `offsets`, left). A right rotate by `r` is a left rotate by `wordBits − r` if you ever need the other direction.
- **Padding is pad10\*1 + a domain byte, with NO length suffix.** Do not reuse `append-be64-length@1` (that's Merkle–Damgård). `keccak.pad@1` appends `0x06` (SHA-3) / `0x1F` (SHAKE), zero-fills to a rate multiple, then ORs `0x80` into the last byte. Two merge cases to test against the oracle: the empty message (→ one full pad block) and `len ≡ −1 (mod rate)` (domain + `0x80` collapse into a single `0x86`).
- **All six FIPS-202 functions share ONE Keccak-f[1600]** — build the permutation once and parameterize rate/domain/output. The shared machinery lives in `src/ciphers/keccak-f.ts` (`buildKeccakRounds`/`buildKeccakPermGroup`/`buildAbsorbSteps`); an **empty `prefix`** reproduces SHA3-256's exact `round.0`…`round.23` ids (do not change that — it's what keeps SHA3 saved-doc layout pins + URL-share hashes stable). SHA3-256's digest (256 bits) fits in one 1088-bit rate block, so squeeze is a single `byte-slice`; SHAKE's variable output is an **unrolled** squeeze (below).
- **SHAKE's squeeze is UNROLLED, not an `iterate`.** The port-mode iterate derives its count from `seedInput.length / blockByteLength` (the *input* length); a squeeze's block count comes from the desired *output* length, so an iterate would need a dishonest dummy seed. Unrolling is also more faithful to FIPS 202 Algorithm 8, which breaks *before* the final permutation: for `n = ceil(outputLength/rate)` output blocks there are exactly `n` `byte-slice` extractions and `n−1` Keccak-f permutations — **no trailing wasted permute** (an iterate's per-iteration `chainFeedback` would always run, leaving a dangling permutation). Block 0 is extracted straight off the absorbed `sponge.state`; `perm.j` = Keccak-f(`perm.{j-1}`), block `j` off `perm.j`.
- **SHAKE's domain byte is 0x1F (both variants); the merge case is 0x9F.** `keccak.pad@1` is generic — it computes `domainByte ^ 0x80` for the one-byte-short merge (`0x1F ^ 0x80 = 0x9F`, vs SHA-3's `0x86`), no hardcoded constant. SHAKE128 rate = 168 (capacity 32); SHAKE256 rate = 136 (capacity 64 — same rate as SHA3-256, different function via the domain byte).
- **The absorb/pad narration is rate/domain-specific — do NOT share SHA-3's prose onto SHAKE.** The Keccak-f *round* narration (θρπχι) is pure permutation math and safely shared, but the absorb-split/xor/concat + pad prose names concrete byte counts (SHA-3 says "136 bytes / last 64"; SHAKE128 is 168/32) and the domain byte (0x06 vs 0x1F). `buildAbsorbSteps(rate, narration)` takes the narration as a **caller argument** so each function supplies its own; the KAT is blind to prose, so a wrong "136" on a 168-byte rate is an unguarded defect. (When extracting shared machinery, prove inertness by diffing `JSON.stringify(buildSha3256Spec())` before/after — the KAT only checks the digest, not ids/params/narration.)
- **SHAKE's output length is EDITABLE spec data — resize by STRUCTURAL rebuild, not `editStepParams`.** The output length changes how many `squeeze.perm.{j}` groups exist, so `stores/spec.ts`'s `setShakeOutputLength` rebuilds the whole spec via `setSpecs(buildCanonicalHash(...))` at the `shakeOutputLength` signal (clamped `[1, MAX_SHAKE_OUTPUT]`=512). `resolveHashDefault` builds SHAKE **on demand** at that signal (SHA-256/SHA3 stay in the static `hashDefaults` table), which keeps `isCustomSpec` honest (a pure length change reads "not custom"). The length travels via Save/Share in the `squeeze.truncate` step's `length` param; `applyDocument` syncs the control from a loaded spec.
- **`node:crypto` is the oracle** — it supports `'sha3-256'` and `'shake128'`/`'shake256'` with `{ outputLength }`. Validate the decomposition against it *before* writing tests (`feedback_crypto_verification`), and for a XOF sweep **both** message length AND output length (a message-only sweep leaves the squeeze loop untested). Empty-string SHA3-256 = `a7ffc6f8…f8434a`; SHAKE128("abc",32) = `5881092d…`. SHAKE output is prefix-stable, so the first `k` bytes of `@L` equal `@k`.
- **A top-level GROUP seeding from another GROUP's `"out"` draws a redundant "no frame found" container edge unless the skip-check resolves the seed.** SHAKE's squeeze carry (`perm.{j}.seedInput = port("perm.{j-1}","out")`) is the first such spec. The graph loop-input pass compares "does the seed already reach a descendant leaf?" using the RAW `seedInput` node — a group id — but the real resolved leaf edge's `from` is the deep producing leaf (`perm.{j-1}.round.23.iota`), so the check misses and a value-less `perm.1 → perm.2` container edge gets drawn. Fixed by resolving the seed through `resolveSeedChain` before the descendant check (same redundancy the DES `initial-permutation → rounds` drop removed). If you add another group-to-group carry, `tests/shake-graph-resolution.test.ts` guards it.
- **`ConstantsPanel.collectConsumers` only knows a hand-listed set of aux-reader step types** (`aux-load-bytes@1`, `keccak.iota@1`). A new hybrid-ported step that reads a `cipherConstant` via `meta.auxReadPorts` won't show up as a "consumer" in the constants panel until you add its type there — the graph's aux edges (from `frame.auxRead`) are separate and unaffected.

## cSHAKE / KMAC (NIST SP 800-185)

cSHAKE and KMAC are **not new sponge machinery** — they build a prefixed (KMAC: also suffixed) message string, flip the pad domain byte, then run the *identical* SHAKE absorb fold + squeeze (the shared `buildSpongeSqueeze` in `src/ciphers/sponge.ts`). Everything genuinely new is *upstream* of the pad. The footguns:

- **`encode_string` uses the BIT length, not the byte length.** `encode_string(S) = left_encode(8·len(S)) ‖ S` — the `8·`. This is the single #1 cSHAKE/KMAC bug: a byte-length prefix passes every structural check and silently produces a **wrong digest** (the exact analogue of the Keccak lane-LE footgun above). `encode-string@1` reads the input length at run time and multiplies by 8; `left_encode`/`right_encode` live in `src/core/sp800-185.ts`. Sanity anchors: `left_encode(0)=01 00`, `right_encode(0)=00 01`, `encode_string("")=01 00`, `left_encode(168)=01 A8`, `right_encode(256)=01 00 02`.
- **cSHAKE's domain byte is 0x04 (merge case 0x84), NOT a new pad step.** `keccak.pad@1` is already generic over `domainByte`, so cSHAKE just passes `0x04` (the two-bit `00` suffix + pad start bit). Don't add a pad step.
- **Empty N AND empty S ⇒ cSHAKE IS SHAKE (domain 0x1F), by definition.** SP 800-185 defines `cSHAKE(X,L,"","") = SHAKE(X,L)`. The `buildCshakeSpec` builder branches on this: empty customization emits **no** prefix steps and uses domain `0x1F` — byte-for-byte a SHAKE pipeline (kept under the `cshake…@1` id). If you make N/S editable, emptying both must flip the domain back or the digest is wrong.
- **KMAC's N is the FIXED ASCII "KMAC"** (`4B 4D 41 43`) for both 128 and 256 — never user-editable. Only S is customization, so KMAC's domain is always 0x04 (no SHAKE-reduction branch). KMAC appends `right_encode(L)` where **L is the output length in BITS** (`outputBytes·8`); KMACXOF appends `right_encode(0)` instead — that single value is the only KMAC↔KMACXOF difference.
- **KMAC breaks prefix-stability** (unlike SHAKE/cSHAKE). Because L is bound into the hashed input via `right_encode(L)`, KMAC@32 is NOT a prefix of KMAC@64 — test each output length **independently**.
- **`node:crypto` has NO cSHAKE/KMAC.** The oracle is pycryptodome (`Crypto.Hash.cSHAKE128/256`, `KMAC128/256` — key ≥ 16 bytes) + the NIST SP 800-185 published example values + a from-scratch Keccak sponge (all three agree). Pin the vectors from that reference *before* writing tests (`feedback_crypto_verification`); `node:crypto` can only cross-check the empty-N/S SHAKE reduction. cSHAKE128 Sample #1 (data `00010203`, S "Email Signature", @32) = `c1c36925…`.
- **Customization strings are EDITABLE spec data — structural rebuild, not `editStepParams`** (same posture as SHAKE's output length; both read the shared `shakeOutputLength` signal). `setCshakeCustomization` rebuilds via `setSpecs(buildCanonicalHash(...))`. The strings travel via Save/Share as `constant-load@1` params (`cust.N`/`cust.S`); `readCshakeCustomization` syncs the controls on load.
- **KMAC's key length is VARIABLE and the key field IS the source of truth — do NOT model it as a separate stepper.** `buildKmacSpec(..., keyByteLength)` threads one length into three places: `inputs.key.byteLength`, the `key.load` `aux-load-bytes@1` read width, and — via `encode_string(K)` — the key's `left_encode(8·len)` bit-length prefix. The App commits a new length from the **key field's blur** (`commitKmacKeyLength` → `setKmacKeyLength`, a structural rebuild via the store's `kmacKeyLength` mirror signal), and the **Run path re-syncs defensively** before running. That defensiveness is load-bearing: the runtime's port-length coercion (Slice 1.12) will *silently* pad/truncate `aux["key"]` to the declared `byteLength` and emit only a `__coerce__` frame — so a spec whose declared key length disagrees with the actual key bytes produces a **wrong MAC that looks fine**. A stepper decoupled from the key field would reintroduce exactly this desync; the key field being the sole control is what prevents it. `readKmacKeyLength(spec)` (= `spec.inputs.key.byteLength`) syncs the mirror on document load. Min length 1 (`aux-load-bytes@1` rejects `< 1`); capped at `MAX_KMAC_KEY_LENGTH` (512) for trace legibility.

## Port-flow scope — edges cannot cross a group boundary

**`portInputs` wiring resolves same-scope only; `aux` is the only cross-scope channel.** When the runtime walks a `group` node it allocates a fresh `nodeOutputs` map seeded only from `seedInput` / `groupSeed`. Per-leaf outputs accumulate inside that local map; only the group NODE's aggregate output is published back to the parent scope when the walk returns. A `portInputs` binding that names an upstream node living in a DIFFERENT scope — even a direct parent or a sibling group — throws at runtime:

```
port-input resolution: leaf 'X' input port 'Y' references upstream node 'Z'
which has no recorded outputs in this scope (… same-scope wiring only)
```

This was measured 2026-06-01 while attempting topology "A" for the Speck key schedule (K2d).

**The ONLY channel that crosses a group boundary is the global `aux` map.** A step inside a group can write to a named `aux` key (`aux["roundKey.0"]`); a step in any other scope can read that same key. This is exactly why the decomposed key schedules (AES K1, Speck K2) use the **B-minimal topology**: the schedule lives inside a default-collapsed `key-schedule` group, so its publish leaf's per-round-key outputs are trapped in the group's child scope and cannot be wired to round leaves outside via `portInputs`. B-minimal works precisely because it hands keys off through `aux`, not through port-flow.

**Topology "A" (explicit per-round-key `portInputs` wiring) is currently unbuildable** for any grouped schedule. It requires a group-output-export runtime feature — a way for a group to surface named inner-leaf outputs into the parent scope as named ports on the group node itself — which does not exist yet. Don't redesign a key schedule spec to use topology A and then wonder why nodes outside the group can't see the publish leaf's outputs; they can't until that runtime feature ships.

**SHA-256's cross-round `port()` references are NOT a counterexample.** SHA-256's round bodies (e.g. `port("round.63","out")`) are same-scope siblings — direct children of the iterate, ungrouped — so those references never cross a group boundary. They resolve fine in the same `nodeOutputs` map. Compare with a hypothetical SHA-256 where each round was wrapped in its own `{ kind: "group" }`: in that case cross-round references would fail with the same "no recorded outputs in this scope" error.

**A group can be seeded with exactly ONE value, which is what decides how a round may be grouped.** The body reads its seed as `port(groupId, "in")` — a single binding. So a round that consumes N > 1 independent values cannot be a group without inventing concat/split plumbing at its boundary. This is why Twofish's 4-rail rounds are flat top-level steps, and why ChaCha20 groups **double rounds** rather than quarter rounds: a quarter round takes four words (not representable), while a double round consumes and produces the whole 64-byte state (one value, and its split/concat boundary is honest — the state really is 64 bytes there). Decide this BEFORE authoring a round body; discovering it afterwards means rewiring every leaf.

**Cross-reference:** memory `project_group_scope_port_isolation`; the K2d resolution documented in `docs/plans/key-schedule-decomposition.md`.

## Stream ciphers / ChaCha20

**A cipher's IV width is NOT necessarily its block width.** They coincide for every block cipher — CBC XORs the IV with a block, so an IV must be exactly one block wide — which is why the IV sites all reached for `blockByteLengthFor`. ChaCha20 breaks it: 64-byte block, 16-byte IV (a 32-bit LE counter plus a 96-bit nonce), and no core for `blockByteLengthFor` to read at all. Use **`ivByteLengthFor`** at any site that sizes, defaults or reconciles the IV.

**`reconcileIvWidth` only acts when the width CHANGES.** Switching between two ciphers that both want 16 bytes keeps the old IV. That is harmless while an IV is an opaque block and wrong the moment one has structure: AES → ChaCha20 inherited `00 01 02 03 …`, setting ChaCha's block counter to `0x03020100` instead of 1. The result encrypts and decrypts perfectly self-consistently and matches no published vector — **and every unit test passed, because they all supply the IV explicitly.** It was found by opening the app in a browser. Any cipher whose IV has internal structure must register a `DEFAULT_IV_BYTES_BY_CIPHER` entry and rely on the sacred-input swap in `changeCipher`, not on width reconciliation.

**A stream cipher has no `"single-block"` mode**, so anything resolving a default mode must read `SUPPORTED_CIPHER_MODES_BY_CIPHER[cipher][0]` (`defaultCipherModeFor`) rather than assume the constant. Three sites had the constant hardcoded — `resolveDefault`, `setCipher`, and document load — and each resolved to a spec that does not exist.

**`isStreamCipherMode` (mode) vs `isStreamCipher` (cipher) are different questions.** Almost everything wants the first: it answers "does this pad? does it use an IV?" and already has every call site. The second is needed only *before* a mode is settled — which mode a newly-selected cipher lands in, and whether the mode selector is interactive. Adding call sites to the cipher-keyed one is how the seven-site hazard comes back.

## Pseudo-random generators (the `prng` family)

**`isCipher` is the ONE coupling the compiler cannot check, and every new non-cipher family must subtract itself from it.** Adding a variant to the `SpecsByMode` union is compiler-driven — a `kind` with no `encrypt`/`decrypt` makes `activeSpec`'s `s[mode()]` a type error and `tsc` walks you through every branch. `isCipher` gets none of that: it is a hand-written `a is Cipher` predicate, so a missing `&& !isNewFamily(a)` returns `true` and **TypeScript believes it**, routing the new family into `setCipher`, the `DEFAULT_*_BY_CIPHER` lookups and the padding overlay. RSA shipped this bug once. `tests/prng-family-surface.test.ts` now guards it — and the guard was verified by perturbing the predicate and watching it fail, not by assuming.

**Write the family predicate as membership over the options list, never as a chain of `a === "x" || a === "y"`.** The hazard above is re-armed by every new **variant**, not only by every new family: widen the union, forget an arm, and the predicate returns false for the new variant, so `isCipher` returns true and the compiler believes *that*. `isPrng` reads `ALL_PRNGS` — the same array the dropdown renders — so the union and the predicate cannot drift apart. (`isHash` and `isAsymmetric` are still disjunctions; convert them the next time either gains a member.)

**A generator has no message, so nothing implies how much work to do.** A cipher's iteration count comes from its input length; a seed says only *which* sequence. The requested length reaches the spec as `zero-fill@1`'s **width** (its bytes are never read) bound to the iterate's `seedInput`. Don't reach for `constant-load@1` instead: it documents itself as the emitter of published cryptographic constants, so the trace would tell a learner that a run of zeros is one, and the literal array would ride along in every saved and URL-shared document.

**Ask what prose a length control writes before reusing another family's.** `prngOutputLength` is deliberately a **separate signal** from `shakeOutputLength`, not a reuse: the SHAKE ceiling is chosen for Keccak's squeeze economics, and a user setting a digest length should not silently change how much output a generator produces. Both are **structural rebuilds** (`setSpecs(buildCanonical…)`), never `editStepParams` — and both need a `read…OutputLength(spec)` counterpart wired into `setSpecFromDocument`, or a save/load round-trip leaves the control and the spec disagreeing.

**Trimmed-vs-untrimmed feedback in a generator loop is a semantics choice, not a bug.** Only the FINAL block is ever short, and the final iteration's `chainFeedback` is discarded — so binding it to the trimmed word is byte-indistinguishable at every output length. This is OFB's situation exactly. Wire the untrimmed state anyway (the recurrence is defined on whole words and the trace should show that) but **assert the indistinguishability by perturbation** rather than claiming a failure mode that does not exist; that way a future topology where every block can be short fails loudly.

**`add-mod@1` and `add-mod-32@1` are different steps and the names do not say so.** `add-mod-32@1` is fixed to 2³² because its modulus is the machine word — nothing to wire. `add-mod@1` takes the modulus on an **input port**, which is what a generator needs: the modulus is a design decision the learner edits, not an implementation detail. Do not substitute `add-mod-32@1` + an `and@1` mask for it; that is correct only for power-of-two moduli, and an editable modulus makes it silently wrong the moment someone tries a prime.

**A family-surface suite that iterates the options list passes VACUOUSLY when a variant goes missing from it.** Every assertion in `tests/prng-family-surface.test.ts` loops over `PRNG_OPTIONS`; deleting MT19937 from `ALL_PRNGS` therefore took the file from 28 tests to 26, **all green** — the `isCipher` landmine re-armed with nothing to catch it. Found by actually performing the perturbation the plan called for rather than assuming the guard held. The fix is to pin the runtime list against the keys of a `Record<Prng, …>` table, which the compiler already forces to be exhaustive; that converts a compile-time guarantee into a check on the list every other test trusts. Any family with an options-list-driven suite has the same hole.

**A seeding convention that differs from the family's needs saying so in the file, not just in the code.** `lcg.ts`'s header states the family convention as "x_0 is the seed verbatim, no scrambling, no `init_by_array`". MT19937 **cannot** honor it — its state is 624 words and a 32-bit seed cannot fill them, so `init_genrand`'s expansion is mandatory and part of the published generator. Two things follow that must reach the screen: only 2³² of the 2^19937 states are reachable from a 32-bit seed, and `init_genrand(s)` vs `init_by_array([s])` produce **entirely different streams** from the same number, with real libraries disagreeing about which they use for an integer seed (C++ and numpy-legacy scramble one way, CPython and numpy's modern generators the other). Ship exactly one, name it, and keep the other as a test-only oracle — two seeding modes in the product would *be* the mismatch trap rather than a demonstration of it.

**Not every deliberate monolith is a volume judgement, and the distinction is worth writing down.** `blowfish.key-schedule@1` and `twofish.h-expand@1` are opaque because decomposing them would be illegible. `mt19937.seed@1` and `mt19937.twist@1` are opaque because they are **structurally inexpressible**: the first needs the loop index (`+ i`) and no leaf in this app produces one; the second reads three words of the state where an iterate body sees only its own block. Before reaching for the escape hatch, check which case you are in — and if it is the structural one, say so in the step's own description, or a learner reads the single frame as laziness.

**A perturbation that changes nothing may be telling you something about the algorithm.** Flipping bit 0 of MT19937's `0x9d2c5680` tempering mask left the stream byte-identical, which looked like a dead test. It is not: `y << 7` has its low 7 bits zero by construction, so those mask bits are unreachable **don't-cares**. That fact is exactly why a rotation could stand in for the shift here — and exactly why it must not, since the equivalence evaporates the moment a learner edits a mask. Both halves are now pinned by test. When a perturbation is a no-op, work out why before weakening the test.

**Emitting a generator's raw state can be the honest choice even when the reference implementation does not.** C's `rand()` returns `(state / 65536) % 32768`; the app emits the state. The extraction is C's *workaround* for the low-bit weakness, so performing it would conceal the thing the variant exists to teach. The obligation that creates: **say so in the narration, with both number sequences**, or a learner comparing against a C program finds a discrepancy and reads it as a bug. Pin both in the KAT, deriving the reference implementation's values from the runtime's output rather than from a literal — otherwise a change to what the app emits would leave the relationship test passing as a tautology.

**Assert a value-level teaching claim against the runtime's bytes, and pair it with the contrast.** "Bit 0 alternates" checked against the `BigInt` reference proves only that the reference agrees with itself. Read it out of the emitted stream, and assert alongside it that the *prime*-modulus generator does **not** alternate — otherwise the test attributes the property to one generator rather than to the power-of-two modulus, and would pass on an implementation where everything alternated.

**A generalized spec builder can silently repoint every previously shared URL.** Spec-only saves are byte-stable and feed the URL-share hash, so reflowing a narration string while generalizing a builder changes the shared document without changing one byte of cipher output — invisible to every behavioural test. Split the prose per variant rather than weaving conditionals through it, and **pin the pre-existing variants' serialized specs by hash** (`tests/lcg-kat.test.ts` does; take the digests from the shipped builder *before* refactoring).

**A wrong endpoint label is invisible to the whole suite.** `GraphView.tsx`'s `endpointLabels` memo and `App.tsx`'s `inputLabel`/`outputLabel` are parallel and must agree; nothing in the type system objects to a string that says "plaintext" for a seed. The PRNG arm of the graph memo was found by opening a browser. Prefer positive predicates for the direction question (`hasDirection()`) over stacking `!isHash(a) && !isPrng(a)` — a direction-less family wired into some sites but not others shows a toggle that silently does nothing.

**A generator whose body sits inside a container cannot reach `$input`, and the LCG pattern does not generalize.** The LCGs bootstrap `chainInput` from `port(INPUT_SOURCE_ID, …)`, which works only because their iterate is at top level. The runtime seeds an iterate body's scope with **only that iterate's own `in`/`chain` ports** (`runtime.ts`'s `new Map([[node.id, portMap]])`), so a body leaf cannot see `$input` at all. Aux is the only cross-scope channel: publish the seed in `App.tsx` beside the CBC IV line (`initialAux.set(PRNG_SEED_AUX, …)`, gated on `isPrng` for the whole family rather than one variant) and read it with `aux-load-bytes@1`. Do **not** smuggle it through the iterate's chain alongside the counter — that puts an invariant on the one wire the trace exists to show changing. Any test driving such a spec through `runSpec` must seed that aux itself, or `aux-load-bytes@1` throws (it does not zero-fill, which is the good outcome — a silent zero seed would produce a plausible, wrong, perfectly self-consistent stream).

**Per-variant ceilings: one family can span three orders of magnitude in frame cost.** An LCG spends ~4 frames per 4-byte word; the ChaCha20 CSPRNG spends ~990 per 64-byte block. A single `MAX_*_OUTPUT` therefore cannot serve both — at the LCGs' 1024-byte ceiling the CSPRNG would build ~16,000 frames. Route every clamp through a `maxPrngOutputFor(variant)` helper, and remember the site a stepper-only clamp misses: **switching variants**, where a length chosen under a cheap variant must be re-capped on the way in (`setPrng`), not just when the user touches the control. The same applies to seed width — `SEED_BYTES_BY_PRNG` replaced a single `LCG_WORD_BYTES` check the moment a 32-byte seed arrived, and a looped `toHaveLength(LCG_WORD_BYTES)` assertion in the family-surface test is what catches you.

**When you extract a shared builder so a second algorithm can compose it, capture the existing specs' digests BEFORE the refactor.** Digests taken afterwards pin the post-refactor bytes to themselves and guard nothing. This is the same URL-share hazard as the narration one above, and it is the one irreversible step in such a change — do it as the literal first action.

## Lattice / the NTT (the `lattice` family)

- **The inverse scales by `128⁻¹ mod 3329 = 3303`, NOT `256⁻¹ = 3316`.** There are 256 coefficients, so the wrong constant is the natural guess. ML-KEM's transform runs **seven** layers, not eight, because `q − 1 = 3328 = 2⁸ · 13` admits no primitive 512th root of unity — it stops at 128 degree-1 polynomials, so the factor that accumulates is 2⁷. Using `256⁻¹` produces a perfectly self-consistent transform whose every output is exactly half of correct, and which agrees with no other implementation.
- **The ζ table is stored in CONSUMPTION order (`17^BitRev7(i)`), not ascending exponent.** The whole rotating-cursor design depends on the layers consuming entries strictly in sequence. A table in exponent order gives a transform that is internally consistent and matches nothing.
- **`NTT⁻¹(NTT(f) ∘ NTT(g))` is wrong with an ELEMENT-WISE `∘`.** The transform's output is 128 degree-1 polynomials, the i-th living modulo `X² − γᵢ`, so the pointwise product multiplies *pairs*: `(a₀b₀ + a₁b₁γᵢ) + (a₀b₁ + a₁b₀)X`. This is the classic first mistake in the construction, which is why `tests/ntt-3329-256-kat.test.ts` writes the base-case multiply out rather than assuming it.
- **The per-pair modulus is `γᵢ = ζ^(2·BitRev7(i) + 1)`, NOT `ζᵢ²`.** The plan file said `ζ²` and it is wrong: the missing `+ 1` gives `1, 3328, 1729, 1600, …` where the true table is `17, 3312, 2761, 568, …`. `GAMMAS` in `mlkem-constants.ts` derives it as `ZETAS[i]²·17`. Free second check: `γ[2i] = ZETAS[64+i]` and `γ[2i+1] = q − ZETAS[64+i]`, so the published ζ table re-verifies the γ one.
- **`Compress_d`/`Decompress_d` round to NEAREST with ties UP, and only decompression can ever hit a tie.** `q` is odd, so `2^(d+1)·x` and `q` are never congruent mod `2q`; `2^d` is even, so `d = 1, y = 1` lands on exactly `1664.5` and must become 1665. The consequence that bites: a *truncating* compressor passes every tie-focused spot check you would think to write. Do the rounding in exact integers — `q/2^d` is not representable, so a `Math.round` oracle disagrees with the spec at values nobody spot-checks.
- **`Compress(Decompress(y)) = y` holds only while `2^d ≤ q`.** At `d = 12` there are 4096 bucket indices and 3329 values, so it is pigeonhole-impossible regardless of rounding — which is exactly why FIPS 203 defines the pair for `d < 12` only and gives the uncompressed case `ByteEncode_12` instead. Verify this property, don't assume it.
- **Write FIPS 203's `m` as `min(2^d, q)`, never as a `d === 12` branch.** The rule exists because 12 bits can carry 4095, which is not a ring element. The min reproduces it exactly at `q = 3329` and keeps behaving sensibly when a learner edits `q`; a hardcoded 12 goes quietly wrong.
- **`ByteEncode`/`ByteDecode`/`SamplePolyCBD` bit order is FIXED by the spec (LSB-first) and is NOT the `littleEndian` param.** That param describes the bytes *within one coefficient* and decides which numbers are read; the bit stream decides how they are packed. Tangling them yields a self-consistent encoding that matches nobody, and P3's aggregate `ek` comparison only catches it in combination with everything else.
- **`node:crypto`'s ML-KEM keygen IGNORES its `seed` option on Node v24.14.1 — but determinism is reachable by IMPORTING rather than generating.** `generateKeyPairSync("ml-kem-768", { seed })` accepts the option silently and returns a different key every call. P2 concluded the deterministic oracle did not exist; P3 disproved that. A hand-assembled PKCS#8 carrying the seed arm of the ML-KEM `PrivateKey` CHOICE imports cleanly and is fully deterministic — **the `[0]` tag must be IMPLICIT** (`0x80 0x40 <64 bytes>` inside the outer OCTET STRING); the EXPLICIT `0xa0` spelling and a bare OCTET STRING are both rejected as `error:1E08010C:DECODER routines::unsupported`. The exported form uses the *both* arm (`SEQUENCE { OCTET STRING (64) seed, OCTET STRING (2400) expandedKey }`), so a seed is recoverable from any generated key and the two halves cross-check. CI is on Node 22 and has no ML-KEM at all — capture any `node:crypto` artifact as a byte fixture (`tests/fixtures/ml-kem-768-seed-vectors.json`) rather than generating it in a test.
- **The forward and inverse butterflies are different shapes, not one shape with a sign flipped.** Cooley–Tukey multiplies *before* combining (`t = ζ·hi; lo′ = lo + t; hi′ = lo − t`); Gentleman–Sande combines *after* (`lo′ = lo + hi; hi′ = ζ·(hi − lo)`). Note also that the forward's two lines both read the ORIGINAL `lo` — overwriting it first makes `hi′` come out as `lo + 2t`, the standard hand-implementation bug.
- **`q` cannot reach a butterfly through a port.** The vector leaves live inside a layer's `iterate`, and the runtime seeds a body scope with only that iterate's own `in`/`chain` ports. `q` rides `spec.cipherConstants` (materialised into the global aux map) and each body reads it with `aux-load-bytes@1`. See the "Port-flow scope" section above — this is the same rule the ChaCha20 CSPRNG's seed and Twofish's subkeys hit.
- **`zq-vec-*@1` are NOT `add-mod@1` / `mod-mul@1` with wider ports.** Those read a whole port as ONE big-endian integer, so a 512-byte polynomial becomes a single 4096-bit number — well-defined arithmetic with nothing to do with polynomials. The `coeffBytes` element width is the entire difference. Their params are `{ coeffBytes, littleEndian }`; `zq-vec-mul-scalar@1`'s contract is function-form (its `scalar` port declares its width from `coeffBytes`), so a new entry was needed in `tests/byte-native-ports-contract.test.ts`'s `KITCHEN_SINK`.
- **There are no negative numbers in `Z_q`.** `3 − 5` is `3327`, not `−2`. Output that looks like large values is small negative ones; subtract `q`.
- **The NTT is the first spec with SEVEN SIBLING `iterate`s, and it broke a UI reading that had been correct by accident.** Anything asking "how many blocks does this trace have?" by taking the maximum `blockIndex` across the whole trace was right only because every prior spec had exactly one loop. Scope such questions to the frame's own container (`iterateScopeKey` in `core/step-id.ts`). Related: **`TraceFrame.path` does NOT include the leaf's own id** — that rides `stepId` — despite what the field's comment claimed until 2026-08-09.
- **It is also the first iterate whose chain width differs from its block width** (a fixed 256-byte ζ table against blocks running 512 → 8). `runtime.ts` never checks, but that was read-verified before it was run-verified; spike novel wiring with existing primitives first.
- **Embedding an existing spec N times means PREFIXING every node id — and the collision is SILENT.** K-PKE puts six NTTs in one spec. The flat trace keys frames by `stepId`, so six nodes called `layer1.split` do not throw: they produce a duplicate-keyed trace, which takes out the scrubber, frame preservation and the graph derivation with no error message anywhere. `buildNttNodes`/`buildNttGroup` take a prefix. **Assert uniqueness over the SHIPPED spec, not over two synthetic helper calls** — the helper is not where the near-misses live.
- **`A[i][j] = SampleNTT(ρ ‖ j ‖ i)` in K-PKE.KeyGen but `ρ ‖ i ‖ j` in K-PKE.Encrypt.** That two-byte swap IS the transpose; there is no transposing step anywhere. Apply it in both places or in neither and you get a key pair that encrypts and decrypts its own messages perfectly and interoperates with nothing. The signature: ρ and `dk_PKE` stay correct while `ek` goes wrong.
- **`G(d ‖ k)`, not `G(d)`** — the FIPS 203 *draft* omitted the parameter byte and the final standard does not. OpenSSL implements the final. Getting it wrong breaks ρ, so nothing downstream can be trusted, which is why ρ is worth checking as its own checkpoint before anything else.
- **`SampleNTT`'s loop condition must be the ACCEPTED-COEFFICIENT count, never a block count.** ~1 candidate in 6 exceeds `q` and is discarded, so the bytes a draw consumes is a random variable with no fixed bound — the same failure class as an undersized RSA square-and-multiply unroll. And **"needs more than two squeeze blocks" is a VACUOUS assertion**: acceptance is ~81%, so 256 coefficients need ~473 bytes and *every* draw already spends three 168-byte blocks. Measured over 162 draws: 160 take three, 2 take four. Assert that the count VARIES.
- **`Compress₁` is the decision step, and it is why the noise has to be small.** Decryption ends by rounding every coefficient of `w` to whichever of 0 or `⌈q/2⌉` it is nearer. Everything upstream — the size of η, the compression widths `du`/`dv` — exists to keep the accumulated error under half a bucket so that rounding lands on the right side.

## Tooling / shell

- **Don't redirect native command stderr in PowerShell with `2>&1`.** PowerShell 5.1 wraps stderr lines in `NativeCommandError` records and sets `$?` to false even on success exit code 0. Capture stdout only, or merge in a different way.
- **…and the flip does NOT require a redirect.** `git commit` with **no redirect at all** reported failure while its pre-commit hook passed — the hook's own progress output goes to stderr, and that is enough. This is expensive to misread: it looks exactly like a real gate failure, and the honest response (re-run the whole ~100 s suite to find the "failing" test) finds nothing wrong. Tell: the reported failure has no failing test named anywhere in the output. **Run any git command whose hooks produce output through the Bash tool instead**, where the exit code is the process's own: `git commit -F msg.txt > /tmp/commit.log 2>&1; echo "EXIT=$?"`.
- **Long commit messages go through `git commit -F <file>`, never a here-string.** The PowerShell tool's transport mangles `@'…'@` around a multi-line `-m` argument — the quoting is stripped and git reads each line as a pathspec, so it fails with a wall of `error: pathspec '…' did not match any file(s)`. Write the message with the Write tool (which is also what keeps escapes intact) and pass `-F`.
- **A stale `npm run dev` server makes Playwright smokes show OLD behavior.** `playwright.config.ts` sets `webServer.reuseExistingServer`, so if a dev server is already listening on **5173** (from a prior session or the user's own `npm run dev`), Playwright reuses it instead of booting fresh — and a fresh page-load against that server can serve pre-edit code.
